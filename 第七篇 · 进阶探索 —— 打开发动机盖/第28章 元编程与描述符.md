#### 开篇：照片 vs 3D打印机

Java老兵对反射（Reflection）再熟悉不过——`Class`对象能告诉你类的结构：有哪些字段、方法、构造器。但Java的`Class`是只读的，你不能用它创建新类，也不能在运行时修改类结构。Java的反射像照片：拍好了只能看，不能改。

Python的元编程截然不同。`type`不仅能告诉你类的结构，还能**创建新类**、**修改类结构**、**拦截类创建过程**。Python的`type`像3D打印机：可以打印出新的类，甚至修改打印过程本身。

这种差异的根源在于Python的"万物皆对象"哲学——类本身也是对象，是`type`的实例。`type`本身也是一个类，而且是自己的实例（`type`是`type`的实例，这不是bug而是设计）。这让Python的元编程能力远超Java反射，是Django ORM、SQLAlchemy、Pydantic等框架"声明式编程"的基石。

> 💡 比喻：Java的`Class`对象像照片——拍好了只能看，不能改，你能检查照片里有什么（字段、方法），但不能把照片里的人改掉。Python的`type`像3D打印机——不仅能检查"打印模板"（类结构），还能打印出新的类，甚至改造打印机本身的打印流程（元类）。Django ORM就是用3D打印机把`class User(models.Model)`自动"打印"成带完整数据库操作能力的类。

#### 第1节 元类：类的类

##### 1.1 类也是对象

在Python中，**类也是对象**——类是`type`的实例。这听起来像绕口令，但这是Python元编程的根基。

```python
# 验证：类是type的实例
class Dog:
    def bark(self):
        return "Woof!"

print(type(Dog))        # <class 'type'>
print(isinstance(Dog, type))  # True

# type本身也是type的实例（自指）
print(type(type))       # <class 'type'>
print(isinstance(type, type))  # True —— 这不是bug，是设计
```

`type`有双重身份：
- 用一个参数调用时，`type(obj)`返回`obj`的类型（等价于`obj.__class__`）
- 用三个参数调用时，`type(name, bases, dict)`**动态创建新类**

```python
# type的三参数形式：动态创建类
Dog = type('Dog', (object,), {
    'bark': lambda self: 'Woof!',
    'species': 'Canis lupus'
})

dog = Dog()
print(dog.bark())      # Woof!
print(dog.species)     # Canis lupus

# 这两种写法完全等价：
# 写法1：class语句
class Dog:
    species = 'Canis lupus'
    def bark(self):
        return 'Woof!'

# 写法2：type()动态创建
Dog = type('Dog', (object,), {
    'species': 'Canis lupus',
    'bark': lambda self: 'Woof!'
})
```

Java的`Class`对象没有这种能力——你不能用`Class`创建新类，只能用`javac`编译`.java`文件或用字节码操作库（如ASM、ByteBuddy）。Python的`type`让"运行时创建类"成为语言原生能力。

##### 1.2 元类：拦截类创建过程

元类（metaclass）是"类的类"——当Python执行`class`语句时，它调用元类来创建类对象。默认元类是`type`，但你可以用自定义元类拦截类创建过程。

```python
# 自定义元类：拦截类创建
class LoggingMeta(type):
    """元类：记录所有类的创建"""
    def __new__(mcs, name, bases, namespace, **kwargs):
        print(f"正在创建类: {name}")
        print(f"  父类: {bases}")
        print(f"  属性: {list(namespace.keys())}")
        # 可以修改namespace——添加、删除、修改属性
        namespace['created_by'] = 'LoggingMeta'
        return super().__new__(mcs, name, bases, namespace, **kwargs)

# 使用元类
class Animal(metaclass=LoggingMeta):
    pass
# 输出: 正在创建类: Animal

class Dog(Animal):
    def bark(self):
        return 'Woof!'
# 输出: 正在创建类: Dog

print(Dog.created_by)  # LoggingMeta（元类自动添加的属性）
```

##### 1.3 类创建的完整流程

当Python执行`class`语句时，它经历以下步骤[^descriptor-guide]：

```
class MyClass(Base, metaclass=Meta):
    x = 1
    def method(self): ...
```

| 步骤 | 调用 | 时机 | 作用 |
|------|------|------|------|
| 1. 确定元类 | 解析`metaclass=`参数和继承链 | 类体执行前 | 决定用哪个元类创建类 |
| 2. `__prepare__` | `Meta.__prepare__(name, bases)` | 类体执行前 | 返回类体的命名空间（默认是dict） |
| 3. 执行类体 | 在`__prepare__`返回的命名空间中执行 | — | 收集属性和方法到命名空间 |
| 4. `__new__` | `Meta.__new__(mcs, name, bases, namespace)` | 类体执行后 | 创建并返回类对象 |
| 5. `__init__` | `Meta.__init__(cls, name, bases, namespace)` | `__new__`之后 | 初始化已创建的类对象 |
| 6. `__set_name__` | 对所有描述符调用`desc.__set_name__(cls, name)` | 类创建后 | 让描述符知道自己叫什么名字 |
| 7. `__init_subclass__` | `Base.__init_subclass__(cls, **kwargs)` | 类创建后 | 通知父类有子类被创建 |

```python
# 完整的生命周期追踪
class TracingMeta(type):
    def __prepare__(mcs, name, bases, **kwargs):
        print(f"1. __prepare__: 为 {name} 准备命名空间")
        return super().__prepare__(name, bases, **kwargs)

    def __new__(mcs, name, bases, namespace, **kwargs):
        print(f"2. __new__: 创建类对象 '{name}'")
        return super().__new__(mcs, name, bases, namespace, **kwargs)

    def __init__(cls, name, bases, namespace, **kwargs):
        print(f"3. __init__: 初始化类 '{name}'")
        super().__init__(name, bases, namespace, **kwargs)

    def __call__(cls, *args, **kwargs):
        print(f"4. __call__: 创建 {cls.__name__} 的实例")
        return super().__call__(*args, **kwargs)

class MyClass(metaclass=TracingMeta):
    pass
# 输出（类定义时）:
# 1. __prepare__: 为 MyClass 准备命名空间
# 2. __new__: 创建类对象 'MyClass'
# 3. __init__: 初始化类 'MyClass'

obj = MyClass()
# 输出（实例化时）:
# 4. __call__: 创建 MyClass 的实例
```

> 💡 关键理解：`__prepare__`、`__new__`、`__init__`在**类定义时**执行（`class`语句执行时），`__call__`在**实例化时**执行（`MyClass()`调用时）。混淆这两个时机是元类bug的头号来源。

##### 1.4 `__init_subclass__`：元类的轻量替代

Python 3.6引入了`__init_subclass__`（PEP 487），为很多过去需要元类的场景提供了更简单的替代方案[^pep-487]。

```python
# Python 3.6+ (PEP 487): __init_subclass__ 替代元类
class PluginBase:
    _plugins = []

    def __init_subclass__(cls, **kwargs):
        super().__init_subclass__(**kwargs)
        PluginBase._plugins.append(cls)
        print(f"插件注册: {cls.__name__}")

class AudioPlugin(PluginBase):
    pass
# 输出: 插件注册: AudioPlugin

class VideoPlugin(PluginBase):
    pass
# 输出: 插件注册: VideoPlugin

print(PluginBase._plugins)  # [<class 'AudioPlugin'>, <class 'VideoPlugin'>]
```

`__init_subclass__` vs 元类：

| 维度 | `__init_subclass__` | 元类 |
|------|---------------------|------|
| 触发时机 | 子类创建后 | 类创建过程中（`__new__`/`__init__`） |
| 能否修改类结构 | 不能（类已创建） | 能（`__new__`中可修改namespace） |
| 能否控制命名空间 | 不能 | 能（`__prepare__`） |
| 能否替换类对象 | 不能 | 能（`__new__`可返回不同对象） |
| 复杂度 | 低 | 高 |
| 适用场景 | 子类注册、钩子 | 框架级类 transformation |

> 💡 建议：优先用`__init_subclass__`，只有当你需要在类创建**之前**修改命名空间、或需要`__prepare__`控制属性顺序时，才用元类。Django ORM和Pydantic用元类是因为它们需要在类创建时扫描类型注解并生成字段描述符——这必须在`__new__`中完成。

#### 第2节 描述符协议：`@property`的底层机制

##### 2.1 什么是描述符

描述符（descriptor）是实现描述符协议的对象——实现了`__get__`、`__set__`、`__delete__`中任意一个方法的类，其实例作为**类属性**时，会拦截属性访问[^descriptor-guide]。

```python
# 描述符协议
class Descriptor:
    def __get__(self, obj, objtype=None):
        """拦截 obj.attr 或 Class.attr 的读取"""
        ...

    def __set__(self, obj, value):
        """拦截 obj.attr = value 的赋值"""
        ...

    def __delete__(self, obj):
        """拦截 del obj.attr 的删除"""
        ...
```

描述符分两种：

| 类型 | 实现的方法 | 优先级 | 典型用途 |
|------|-----------|--------|---------|
| 数据描述符（data descriptor） | `__get__` + `__set__`/`__delete__` | 高于实例字典 | `@property` |
| 非数据描述符（non-data descriptor） | 仅`__get__` | 低于实例字典 | 方法绑定 |

**优先级规则**（属性查找顺序）：

```
obj.x 的查找顺序:
1. 数据描述符（type(obj).__mro__中定义的__get__+__set__）
2. 实例字典 obj.__dict__['x']
3. 非数据描述符（type(obj).__mro__中定义的仅__get__）
4. 类变量 type(obj).__dict__['x']
5. __getattr__（如果定义了）
```

这意味着：数据描述符（如`@property`）永远优先于实例字典——你无法在实例上覆盖它。非数据描述符（如方法）可以被实例字典覆盖——这就是为什么实例可以"覆盖"方法。

##### 2.2 用描述符实现`@property`

`@property`的底层就是一个数据描述符：

```python
# 手动实现 @property 的核心逻辑
class MyProperty:
    def __init__(self, fget=None, fset=None, fdel=None):
        self.fget = fget
        self.fset = fset
        self.fdel = fdel

    def __get__(self, obj, objtype=None):
        if obj is None:  # Class.prop 访问（返回描述符本身）
            return self
        if self.fget is None:
            raise AttributeError("unreadable attribute")
        return self.fget(obj)

    def __set__(self, obj, value):
        if self.fset is None:
            raise AttributeError("can't set attribute")
        self.fset(obj, value)

    def __delete__(self, obj):
        if self.fdel is None:
            raise AttributeError("can't delete attribute")
        self.fdel(obj)

    def setter(self, fset):
        return type(self)(self.fget, fset, self.fdel)

    def deleter(self, fdel):
        return type(self)(self.fget, self.fset, fdel)

# 使用（和内置@property行为一致）
class Person:
    def __init__(self, name):
        self._name = name

    @MyProperty
    def name(self):
        return self._name

    @name.setter
    def name(self, value):
        if not value:
            raise ValueError("name不能为空")
        self._name = value

p = Person("Alice")
print(p.name)     # Alice（调用__get__ → fget）
p.name = "Bob"    # 调用__set__ → fset
p.name = ""       # ValueError: name不能为空
```

##### 2.3 方法绑定：函数也是描述符

Python的方法绑定（`self`自动传入）也是描述符实现的。普通函数是**非数据描述符**——它的`__get__`方法把函数绑定到实例，生成bound method。

```python
# 函数的 __get__ 实现了方法绑定
class Function:
    def __get__(self, obj, objtype=None):
        if obj is None:
            return self  # Class.method 返回函数本身
        return MethodType(self, obj)  # obj.method 返回绑定的方法

# 验证：
class MyClass:
    def method(self):
        return self

obj = MyClass()

# 类访问：返回原始函数（非数据描述符的__get__ with obj=None）
print(MyClass.method)        # <function MyClass.method>

# 实例访问：返回bound method（__get__绑定了self）
print(obj.method)            # <bound method MyClass.method of <MyClass object>>
print(obj.method() is obj)   # True（self自动传入）
```

这就是为什么`obj.method()`等价于`MyClass.method(obj)`——描述符协议自动完成了`self`的绑定。Java的方法绑定是编译器在字节码层面处理的，Python则用描述符协议在运行时动态完成。

##### 2.4 `__set_name__`：描述符的自我认知

Python 3.6引入了`__set_name__`（PEP 487），让描述符知道自己被赋给了什么名字[^pep-487]：

```python
class ValidatedField:
    """验证描述符：自动知道自己的字段名"""
    def __set_name__(self, owner, name):
        self.name = name
        self.private_name = f'_{name}'

    def __get__(self, obj, objtype=None):
        if obj is None:
            return self
        return getattr(obj, self.private_name, None)

    def __set__(self, obj, value):
        self.validate(value)
        setattr(obj, self.private_name, value)

    def validate(self, value):
        raise NotImplementedError

class PositiveInt(ValidatedField):
    def validate(self, value):
        if not isinstance(value, int) or value <= 0:
            raise ValueError(f"{self.name}必须是正整数")

class NonEmptyStr(ValidatedField):
    def validate(self, value):
        if not isinstance(value, str) or not value:
            raise ValueError(f"{self.name}必须非空字符串")

class Person:
    age = PositiveInt()      # __set_name__自动调用：self.name = 'age'
    name = NonEmptyStr()     # __set_name__自动调用：self.name = 'name'

p = Person()
p.age = 30     # ✅
p.age = -1     # ValueError: age必须是正整数
p.name = "Alice"  # ✅
p.name = ""       # ValueError: name必须非空字符串
```

在`__set_name__`之前（Python 3.5及以下），描述符不知道自己的名字，必须手动传入：

```python
# Python 3.5及以下的写法（繁琐）
class PositiveInt:
    def __init__(self, name):
        self.name = name  # 必须手动传入字段名

class Person:
    age = PositiveInt('age')    # 重复写'age'
    name = PositiveInt('name')  # 重复写'name'
```

`__set_name__`让描述符声明更简洁——这正是Django ORM字段声明的基础。Django的`models.CharField(max_length=100)`不需要传入字段名，`__set_name__`自动处理。

#### 第3节 `@dataclass`：元编程的日常应用

##### 3.1 PEP 557：数据类

Python 3.7引入了`@dataclass`装饰器（PEP 557），用元编程自动生成`__init__`、`__repr__`、`__eq__`等方法[^pep-557]。这是Java程序员最应该了解的元编程应用——它让Python的数据类声明接近Java的`record`。

```python
from dataclasses import dataclass

@dataclass
class Person:
    name: str
    age: int
    email: str | None = None

# 自动生成的等价代码：
# def __init__(self, name: str, age: int, email: str | None = None):
#     self.name = name
#     self.age = age
#     self.email = email
#
# def __repr__(self):
#     return f"Person(name={self.name!r}, age={self.age!r}, email={self.email!r})"
#
# def __eq__(self, other):
#     if self.__class__ == other.__class__:
#         return (self.name, self.age, self.email) == (other.name, other.age, other.email)
#     return NotImplemented

p = Person("Alice", 30)
print(p)  # Person(name='Alice', age=30, email=None)
print(p == Person("Alice", 30))  # True
```

```java
// Java 16+ record（等价写法）
public record Person(String name, int age, String email) {}
// 自动生成：构造器、toString、equals、hashCode
```

##### 3.2 `@dataclass`的元编程原理

`@dataclass`不是元类——它是装饰器。它通过检查类的`__annotations__`（类型注解字典）来发现字段，然后用`exec`动态生成方法并设置到类上[^pep-557]。

```python
# @dataclass 的简化原理
def my_dataclass(cls):
    # 1. 扫描类型注解，发现字段
    fields = {name: type_hint for name, type_hint in cls.__annotations__.items()
              if not name.startswith('_')}

    # 2. 动态生成 __init__
    params = ', '.join(fields.keys())
    assignments = '\n    '.join(f'self.{name} = {name}' for name in fields)
    init_code = f'def __init__(self, {params}):\n    {assignments}'
    exec(init_code, cls.__dict__, locals())
    cls.__init__ = locals()['__init__']

    return cls

@my_dataclass
class Person:
    name: str
    age: int

p = Person("Alice", 30)
print(p.name, p.age)  # Alice 30
```

| 维度 | Java `record` | Python `@dataclass` |
|------|---------------|---------------------|
| 实现方式 | 编译器生成 | 运行时装饰器（元编程） |
| 可变性 | 不可变（final字段） | 默认可变，`frozen=True`不可变 |
| 继承 | 不可继承record | 可继承普通类 |
| 生成的method | 构造器、equals、hashCode、toString | `__init__`、`__repr__`、`__eq__`等 |
| 自定义方法 | 不可添加 | 可添加 |
| 何时生成 | 编译期 | 运行时（类定义时） |

##### 3.3 `@dataclass`高级特性

```python
from dataclasses import dataclass, field

@dataclass(frozen=True)  # 不可变（生成__hash__）
class Point:
    x: float
    y: float

@dataclass
class Employee:
    name: str
    salary: float
    # 默认值用field（避免可变默认值陷阱）
    skills: list[str] = field(default_factory=list)
    # 排除某个字段不参与init
    internal_id: int = field(default=0, repr=False, compare=False)

    def __post_init__(self):
        """init后调用的钩子——可以做额外初始化"""
        if self.salary < 0:
            raise ValueError("薪资不能为负")

emp = Employee("Alice", 50000, skills=["Python", "Java"])
print(emp)  # Employee(name='Alice', salary=50000, skills=['Python', 'Java'])
```

> 💡 Java程序员注意：Python的可变默认值陷阱在`@dataclass`中通过`field(default_factory=...)`解决。直接写`skills: list[str] = []`会触发`ValueError`——`@dataclass`主动拦截了这个经典Python陷阱。

#### 第4节 Java反射 vs Python元编程

##### 4.1 能力对比

| 维度 | Java反射 | Python元编程 |
|------|---------|------------|
| 创建类 | 不能（需编译或字节码库） | `type()`可创建 |
| 修改类 | 不能（Class不可变） | 可动态添加/删除属性方法 |
| 拦截类创建 | 不能 | 元类`__new__`/`__init__` |
| 拦截属性访问 | 不能 | 描述符`__get__`/`__set__` |
| 注解处理 | 运行时反射注解 | 运行时读`__annotations__` |
| 性能 | 慢（反射查找） | 中等（`__dict__`操作） |
| 典型框架 | Spring（IoC/AOP） | Django ORM/SQLAlchemy/Pydantic |

##### 4.2 Spring vs Django ORM：元编程的不同战场

Spring用Java反射实现依赖注入和AOP——扫描类的注解（`@Autowired`、`@Service`），运行时通过反射调用方法。但Spring不能创建新类或修改类结构——它只能在已有类上"操作"。

Django ORM用Python元编程实现"声明式数据库映射"——`class User(models.Model)`在类创建时，元类扫描字段定义（`models.CharField`），自动生成数据库表schema、查询API、表单等。这不仅是"操作"已有类，而是"改造"类本身。

```python
# Django ORM：元类在类创建时自动生成数据库操作
from django.db import models

class User(models.Model):
    name = models.CharField(max_length=100)
    email = models.EmailField(unique=True)
    age = models.IntegerField(default=0)

# 元类在类创建时做了什么：
# 1. 扫描所有 models.Field 实例（描述符）
# 2. 收集到 _meta.fields
# 3. 为每个字段生成数据库列定义
# 4. 自动生成 User.objects (Manager)
# 5. 自动生成查询方法：User.objects.filter(), .get(), .create() 等

# 使用时，你获得的是完整的数据库操作能力：
User.objects.create(name="Alice", email="alice@example.com", age=30)
users = User.objects.filter(age__gte=18)
```

```java
// Java的等价（JPA/Hibernate）：用注解+反射，不修改类
@Entity
public class User {
    @Column(name = "name", length = 100)
    private String name;

    @Column(unique = true)
    private String email;

    @Column(columnDefinition = "integer default 0")
    private int age;

    // 必须手写getter/setter（或用Lombok）
    public String getName() { return name; }
    public void setName(String name) { this.name = name; }
    // ...
}
// Hibernate通过反射读取注解，生成SQL，但User类本身不变
```

| 维度 | Spring/Hibernate（Java） | Django ORM（Python） |
|------|------------------------|---------------------|
| 机制 | 注解 + 反射 | 元类 + 描述符 |
| 类是否被修改 | 否（只读注解） | 是（元类添加方法/属性） |
| 字段定义 | `@Column`注解 | `models.CharField()`描述符 |
| getter/setter | 必须手写（或Lombok） | 自动生成（描述符拦截） |
| 查询API | JPQL/Criteria API | `objects.filter()`链式调用 |
| 启动时扫描 | 是（组件扫描） | 否（类定义时即时处理） |

> 💡 比喻：Java的Hibernate像"质检员"——检查产品（类）上的标签（注解），根据标签决定怎么处理，但产品本身不变。Python的Django ORM像"生产线改造"——在产品（类）出厂前，直接改造生产线（元类），给产品加装新功能（查询方法、字段描述符），出厂的产品已经和设计图纸不同了。

#### 第5节 Pydantic：运行时类型检查的元编程

Pydantic是Python元编程的现代典范——它利用类型注解（PEP 526）在运行时做数据验证，是FastAPI的基石。

```python
from pydantic import BaseModel, Field, validator

class User(BaseModel):
    name: str = Field(min_length=1, max_length=100)
    email: str
    age: int = Field(ge=0, le=150)

    @validator('email')
    def validate_email(cls, v):
        if '@' not in v:
            raise ValueError('email must contain @')
        return v

# Pydantic在类创建时做了什么：
# 1. 元类/__init_subclass__扫描 __annotations__
# 2. 为每个字段创建验证描述符
# 3. 生成 __init__（带验证）
# 4. 生成 .model_dump() / .model_validate() 等方法

# 使用：自动验证
user = User(name="Alice", email="alice@example.com", age=30)
print(user.name)  # Alice

# 类型错误会被拦截
User(name="Alice", email="invalid", age=30)   # email验证失败
User(name="", email="a@b.com", age=200)       # name太短 + age超范围
```

Pydantic证明了Python类型注解的双重价值——既给mypy/pyright做静态检查（第18章），又给Pydantic做运行时验证。Java的注解做不到这一点——Java注解是静态的元数据，不能在运行时自动生成验证逻辑。

#### ⚡ 性能贴士

| 操作 | 普通类属性 | 描述符属性 | 元类创建的类 | 开销 |
|------|-----------|-----------|------------|------|
| 类创建 | ~0.1ms | ~0.1ms | ~1ms | +0.9ms（一次性） |
| 属性读取 | ~35ns | ~50ns | ~50ns | +15ns |
| 属性赋值 | ~35ns | ~50ns | ~50ns | +15ns |
| 方法调用 | ~45ns | ~45ns | ~45ns | 0（方法绑定开销相同） |

**优化建议**：

1. **元类开销是一次性的**：类创建多1ms，但只在import时发生一次。运行时属性访问开销+15ns，可忽略。
2. **`@dataclass`比手写`__init__`慢约5%**：因为`@dataclass`生成的`__init__`有类型检查逻辑。但这5%换来的是代码简洁和正确性，值得。
3. **描述符的`__get__`/`__set__`比直接`__dict__`访问慢约40%**：但这是验证、日志等功能的必要代价。
4. **避免在热路径用`getattr`/`setattr`**：`obj.x`比`getattr(obj, 'x')`快，因为前者是直接字节码操作，后者要经过字符串查找。
5. **`__slots__`可以加速属性访问**：用`__slots__`替代`__dict__`，属性访问从字典查找变为描述符访问，快约30%。

> 💡 性能口诀：元类一次性，描述符微开销，dataclass换简洁，热路径避getattr。

#### 踩坑日记：元类的继承地狱

> 📝 第一人称踩坑记录

"第一次写元类时，我遇到了一个诡异的问题：两个库的基类用了不同的元类，我试图同时继承两者，Python报了`TypeError: metaclass conflict`。

```python
class BaseA(metaclass=MetaA): ...
class BaseB(metaclass=MetaB): ...

class Child(BaseA, BaseB): ...  # TypeError: metaclass conflict
```

我花了半天理解：Python要求一个类的所有父类的元类之间必须有继承关系。`MetaA`和`MetaB`没有继承关系，Python不知道用哪个。

解决方案是创建一个组合元类：

```python
class CombinedMeta(MetaA, MetaB): pass

class Child(BaseA, BaseB, metaclass=CombinedMeta): ...
```

但这又引出了新问题——`MetaA.__new__`和`MetaB.__new__`的调用顺序、它们是否兼容、是否重复处理……最终我把整个设计推翻重做，用`__init_subclass__`替代了元类，问题消失。

教训：**能用`__init_subclass__`解决的，不要用元类。** 元类是框架级别的工具，业务代码几乎不需要。当你觉得需要元类时，先问自己：`__init_subclass__`能不能做到？"

#### 思维实验

> 🤔 思考题：如果Python像Java一样，类在编译期确定且运行时不可变（不能动态添加属性、不能用元类拦截类创建），Django ORM还能实现`class User(models.Model)`自动生成数据库操作吗？如果不能，Django ORM会变成什么样？

提示：思考Django ORM的`models.CharField()`是如何在类定义时被元类收集并转化为数据库字段的。如果不能用元类，开发者需要怎样声明字段？参考Hibernate的`@Entity`+`@Column`注解方式，思考声明式编程的"声明"和"执行"在两种语言中分别发生在什么时候。

#### 本章小结

1. **类也是对象**：Python的类是`type`的实例，`type`可以动态创建类 —— vs Java的`Class`对象只读不可创建，像照片vs 3D打印机
2. **元类拦截类创建**：`__prepare__`→`__new__`→`__init__`→`__call__`构成完整的类生命周期 —— 框架级类transformation的基石
3. **描述符是属性访问的拦截器**：`@property`、方法绑定、`@classmethod`/`@staticmethod`底层都是描述符协议 —— 数据描述符优先于实例字典，非数据描述符反之
4. **`__init_subclass__`优先于元类**：PEP 487的`__init_subclass__`覆盖了80%的元类场景，更简单更安全 —— 能用它就别用元类
5. **`@dataclass`是元编程的日常**：PEP 557的`@dataclass`用装饰器+类型注解自动生成样板方法 —— Python版的Java `record`，但更灵活
6. **Django ORM/Pydantic是元编程的巅峰**：用元类+描述符实现"声明式编程" —— `class User(models.Model)`一行代码生成完整数据库API，这是Java反射做不到的

Java的反射是"看但不能改"，Python的元编程是"看而且能改"——这是动态语言的终极自由，也是Django/SQLAlchemy/Pydantic等框架声明式编程的根基。

[^descriptor-guide]: Raymond Hettinger, "Descriptor Guide", Python Official Documentation, https://docs.python.org/3/howto/descriptor.html — 描述符是Python属性访问的底层机制，实现了`__get__`/`__set__`/`__delete__`中任意方法的类即为描述符。数据描述符（有`__set__`或`__delete__`）优先于实例字典，非数据描述符（仅有`__get__`）低于实例字典。`@property`、方法绑定、`@classmethod`/`@staticmethod`底层都是描述符。

[^pep-487]: PEP 487: Simpler customisation of class creation, Martin Teichmann, 2017-04-03, https://peps.python.org/pep-0487/ — Python 3.6引入`__init_subclass__`和`__set_name__`。`__init_subclass__`在子类创建时自动调用，为子类注册、钩子等场景提供了比元类更简单的方案。`__set_name__`让描述符自动知道自己被赋值的属性名。

[^pep-557]: PEP 557: Data Classes, Eric V. Smith, 2017-06-16, https://peps.python.org/pep-0557/ — Python 3.7引入`@dataclass`装饰器，基于PEP 526类型注解自动生成`__init__`、`__repr__`、`__eq__`等方法。`@dataclass`不是元类，而是通过检查`__annotations__`并在运行时生成方法的装饰器。
