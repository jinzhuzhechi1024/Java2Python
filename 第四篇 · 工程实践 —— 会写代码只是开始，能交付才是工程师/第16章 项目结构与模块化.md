#### 第1节 项目结构：Maven的"写字楼" vs Python的"创意园区"

Java老兵对Maven的项目结构刻骨铭心——`src/main/java`放业务代码、`src/test/java`放测试、`src/main/resources`放配置文件、`target/`放编译产物。这套结构是Maven强制约定的，偏离约定就意味着插件不识别、构建失败。

Python没有这种强制约定，但社区经过十余年实践，收敛出了一套事实标准——**src layout**。

##### 1.1 现代Python项目结构

```
myproject/
├── pyproject.toml          # 项目配置（≈pom.xml，PEP 621标准）
├── README.md
├── LICENSE
├── uv.lock                 # 依赖锁定文件（≈Maven的依赖树）
├── src/                    # ← 关键：源码放在src/下
│   └── myapp/              # 包名
│       ├── __init__.py     # 包标识文件
│       ├── __main__.py     # python -m myapp 的入口
│       ├── core.py         # 核心业务逻辑
│       ├── models.py       # 数据模型
│       └── utils/          # 子包
│           ├── __init__.py
│           └── logger.py
├── tests/                  # 测试目录（与src/平级）
│   ├── conftest.py         # pytest全局fixture
│   ├── test_core.py
│   └── test_models.py
├── docs/                   # 文档（可选）
└── .venv/                  # 虚拟环境（不提交git）
```

> 💡 比喻：Maven项目像写字楼——`src/main/java`是办公区，`src/test/java`是质检区，`resources`是仓库，严格分区，违反约定就构建不了。Python项目像创意园区——`src/myapp`是你的工作室，`tests`是隔壁的质检室，`.venv`是你私人的工具箱，结构松散但清晰。约定优先于强制，但约定本身已经收敛到最佳实践。

##### 1.2 src layout vs flat layout：一个文件夹的差异

很多Python教程展示的是flat layout——把包目录直接放在项目根目录：

```
# flat layout（不推荐用于正式项目）
myproject/
├── pyproject.toml
├── myapp/                  # ← 包直接在根目录
│   ├── __init__.py
│   └── core.py
└── tests/
    └── test_core.py
```

看起来少了一层嵌套，更简洁。但这个看似微小的差异，隐藏着一个危险的陷阱。

**陷阱：flat layout让测试"假通过"**

当你运行`pytest`时，Python解释器会自动把当前工作目录（`.`）加入`sys.path`。在flat layout下，`import myapp`会直接找到当前目录下的`myapp/`文件夹——而不是你通过`pip install`安装的那个包。

这意味着：

- 如果`pyproject.toml`的打包配置漏掉了某个文件，flat layout下测试照常通过（因为直接import源文件），但用户`pip install`后却会发现文件缺失
- 如果包名配置错误，flat layout下不会暴露问题，直到发布后才在用户环境崩溃
- 数据文件（模板、配置）在开发时通过本地路径能读到，打包后却找不到

src layout通过把源码移到`src/`子目录，彻底杜绝了这个问题——`src/`不在`sys.path`上，所以必须先`pip install -e .`（可编辑安装）才能`import myapp`。这强制测试走真实的安装路径，提前暴露打包问题。[^pypa-src-layout]

| 维度 | flat layout | src layout |
|------|-------------|------------|
| 包位置 | 项目根目录 | `src/`子目录 |
| 测试时import | 直接读源文件（绕过安装） | 必须安装后才能import |
| 打包问题 | 测试"假通过"，发布后暴露 | 测试阶段即暴露 |
| 需要安装步骤 | 不需要 | 需要`pip install -e .` |
| 适用场景 | 一次性脚本、不发布的应用 | 库、CLI工具、任何要发布的项目 |

> ⚡ PyPA（Python Packaging Authority）官方推荐：所有新项目使用src layout。`uv init`从0.12.0版本起默认生成src layout。pytest、pip、Flask、Black、Hatch、attrs等主流项目全部使用src layout。[^pydevtools-src-layout]

##### 1.3 `__init__.py`：包的"门牌号"

Java用目录结构+包声明（`package com.example;`）定义命名空间，Python用`__init__.py`文件标识一个目录是包。

```python
# src/myapp/__init__.py
"""myapp - 一个示例应用包"""

__version__ = "1.0.0"

# 可以在这里做包级别的初始化
from myapp.core import App  # 暴露便捷导入

# 用户可以 from myapp import App，而不需要 from myapp.core import App
```

Python 3.3+引入了命名空间包（PEP 420），允许没有`__init__.py`的目录也被视为包。但对于正式项目，仍然建议显式添加`__init__.py`——它不仅是包标识，还可以做包级别的初始化和便捷导入。

```java
// Java: package声明 + 目录结构共同定义命名空间
package com.example.myapp;

public class App {
    // ...
}
// 对应目录: src/main/java/com/example/myapp/App.java
```

```python
# Python: __init__.py标识包，目录名即包名
# src/myapp/__init__.py 存在 → myapp是一个包
# src/myapp/core.py → myapp.core模块
# 用法: from myapp.core import App
```

#### 第2节 `pyproject.toml`：Python的`pom.xml`

##### 2.1 PEP 621标准

2020年，PEP 621定义了`pyproject.toml`中`[project]`表的标准格式——这是Python打包生态的里程碑，相当于Java世界从Ant的`build.xml`统一到Maven的`pom.xml`。[^pep-621]

PEP 621之前，每个构建工具用自己的格式存元数据：setuptools用`setup.py`（可执行Python代码），Poetry用`[tool.poetry]`，Flit用`[tool.flit.metadata]`。读取项目元数据需要知道用的哪个工具，甚至需要执行代码。PEP 621统一了这一切——所有元数据放在`[project]`表里，任何兼容的构建后端都能读取。

```toml
# pyproject.toml —— Python项目配置文件（PEP 621标准）

[build-system]                    # 构建系统声明（PEP 517/518）
requires = ["hatchling >= 1.26"]  # 构建依赖
build-backend = "hatchling.build" # 构建后端

[project]                         # 项目元数据（PEP 621）
name = "myapp"                    # 必填：项目名（唯一不能设为dynamic的字段）
version = "1.0.0"                 # 必填：版本号（PEP 440格式，可设为dynamic）
description = "A sample application"
readme = "README.md"              # 长描述（README文件路径）
requires-python = ">=3.12"        # Python版本要求
license = {text = "MIT"}          # 许可证
authors = [
    {name = "Zhu", email = "zhu@example.com"}
]
keywords = ["web", "api"]         # 关键词
classifiers = [                   # PyPI分类标签
    "Programming Language :: Python :: 3",
    "Programming Language :: Python :: 3.12",
    "License :: OSI Approved :: MIT License",
]
dependencies = [                  # 运行时依赖（PEP 508格式）
    "fastapi>=0.104",
    "uvicorn>=0.24",
    "pydantic>=2.0",
]

[project.optional-dependencies]   # 可选依赖组（相当于Maven的profile）
dev = [
    "pytest>=8.0",
    "mypy>=1.11",
    "ruff>=0.5",
]
docs = [
    "sphinx>=7.0",
    "sphinx-rtd-theme",
]

[project.scripts]                 # 命令行入口（安装后可直接执行）
myapp = "myapp.__main__:main"     # 安装后可运行 myapp 命令

[project.urls]                    # 项目URL
Homepage = "https://github.com/user/myapp"
Repository = "https://github.com/user/myapp.git"
"Bug Tracker" = "https://github.com/user/myapp/issues"

# 工具配置也放在同一个文件里
[tool.ruff]                       # Ruff linter配置
line-length = 100
target-version = "py312"

[tool.pytest.ini_options]         # pytest配置
testpaths = ["tests"]
addopts = "-v --tb=short"

[tool.mypy]                       # mypy配置
strict = true
```

对比Maven的`pom.xml`：

```xml
<!-- pom.xml —— Maven项目配置 -->
<project>
    <modelVersion>4.0.0</modelVersion>
    <groupId>com.example</groupId>          <!-- 对应pyproject.toml的name -->
    <artifactId>myapp</artifactId>
    <version>1.0.0</version>                <!-- 对应version -->
    <packaging>jar</packaging>

    <properties>
        <java.version>17</java.version>     <!-- 对应requires-python -->
        <maven.compiler.source>17</maven.compiler.source>
    </properties>

    <dependencies>                          <!-- 对应dependencies -->
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-web</artifactId>
            <version>3.2.0</version>
        </dependency>
    </dependencies>

    <profiles>                              <!-- 对应optional-dependencies -->
        <profile>
            <id>dev</id>
            <dependencies>
                <dependency>
                    <groupId>org.junit.jupiter</groupId>
                    <artifactId>junit-jupiter</artifactId>
                    <scope>test</scope>
                </dependency>
            </dependencies>
        </profile>
    </profiles>

    <build>
        <plugins>                           <!-- 构建插件配置 -->
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-surefire-plugin</artifactId>
            </plugin>
        </plugins>
    </build>
</project>
```

| 特性 | Maven `pom.xml` | Python `pyproject.toml` |
|------|-----------------|------------------------|
| 格式 | XML | TOML（更人类友好） |
| 元数据标准 | Maven自带 | PEP 621（工具无关） |
| 依赖声明 | `<dependencies>` | `[project] dependencies` |
| 可选依赖 | `<profiles>` | `[project.optional-dependencies]` |
| 构建工具配置 | `<build><plugins>` | `[tool.xxx]` 各工具子表 |
| 可执行性 | 不可执行（声明式） | 不可执行（声明式） |
| 一个文件管所有 | ✅ | ✅ |

##### 2.2 支持PEP 621的构建后端

PEP 621只标准化了元数据的格式，构建逻辑由`[build-system]`指定的后端实现。切换后端只需改`[build-system]`，`[project]`表不变：[^pep621-backends]

| 构建后端 | PEP 621支持 | 特点 |
|---------|------------|------|
| Hatchling | 原生支持 | Hatch生态默认后端，功能全面 |
| flit_core | 原生支持 | 极简，适合纯Python库 |
| setuptools | v61.0+ | 老牌工具，兼容性最好 |
| pdm-backend | 原生支持 | PDM生态默认后端 |
| poetry-core | v2.0+（2025年1月） | Poetry生态，同时支持`[tool.poetry]`旧格式 |
| uv_build | 原生支持 | uv自带后端，2024年新增 |

#### 第3节 `import`机制：运行时执行的"函数调用"

这是Java老兵最容易踩坑的地方。Java的`import`是编译期的命名空间引用——它告诉编译器"去classpath找这个类"，不执行任何代码。Python的`import`是运行时操作——它**执行**目标模块的顶层代码。

##### 3.1 import的执行过程

```python
# myapp/utils.py
print("utils模块被加载")  # ← 这行在import时就会执行

def helper():
    return "hello"

# main.py
import myapp.utils  # 控制台立刻打印 "utils模块被加载"
```

Python import的完整流程：

1. **检查`sys.modules`缓存**：Python维护一个全局字典`sys.modules`，已导入的模块不会重复执行
2. **搜索模块**：按`sys.path`顺序查找（内置模块 → 标准库 → site-packages → 当前目录）
3. **执行模块代码**：找到后执行模块所有顶层语句，函数/类定义在此阶段完成
4. **编译缓存**：生成`.pyc`文件存入`__pycache__/`，下次跳过编译步骤
5. **注入`sys.modules`**：将模块对象加入缓存，后续import直接返回缓存

```python
import sys

# 第一次import——执行模块代码
import myapp.utils  # 打印 "utils模块被加载"

# 第二次import——从sys.modules缓存返回，不重复执行
import myapp.utils  # 不打印任何内容

# 验证：同一个模块对象
assert sys.modules['myapp.utils'] is myapp.utils  # True
```

| 特性 | Java import | Python import |
|------|------------|--------------|
| 时机 | 编译期 | 运行时 |
| 执行代码 | 不执行 | 执行模块顶层代码 |
| 缓存机制 | classpath查找 | `sys.modules`字典缓存 |
| 循环依赖 | 编译报错 | 运行时可能出错（见下文） |
| 性能 | classpath查找快 | 首次import较慢，`__pycache__`后较快 |
| 条件导入 | 不支持 | 支持（`if TYPE_CHECKING:`下import） |

##### 3.2 循环导入：Python的暗坑

Java的循环依赖在编译期就会报错，你能立刻发现。Python的循环导入是运行时错误——有时报错，有时"侥幸通过"，非常隐蔽。

```python
# myapp/models.py
from myapp.database import db  # ← 导入database模块

class User:
    def save(self):
        db.insert(self)

# myapp/database.py
from myapp.models import User  # ← 导入models模块

class Database:
    def get_user(self, id):
        return User(id=id)

db = Database()
```

如果先`import myapp.models`：
1. Python开始执行`models.py`
2. 遇到`from myapp.database import db`，开始执行`database.py`
3. `database.py`遇到`from myapp.models import User`——但`models.py`还没执行完，`User`类还没定义
4. **`ImportError: cannot import name 'User' from partially initialized module 'myapp.models'`**

**解决方案：延迟导入**

```python
# myapp/models.py —— 不在顶层import database
class User:
    def save(self):
        from myapp.database import db  # ← 延迟到方法内部import
        db.insert(self)

# myapp/database.py
from myapp.models import User  # 现在可以安全import了

class Database:
    def get_user(self, id):
        return User(id=id)

db = Database()
```

> 💡 比喻：Java的循环依赖像两人面对面同时伸手握手——编译器立刻报错"你们俩互相等谁先伸手？"Python的循环依赖像两人通过电话约见面——谁先拨电话谁先到达，但对方可能还没准备好接听。延迟导入相当于"到了再打电话"，避免同时拨号的死锁。

##### 3.3 `TYPE_CHECKING`：只给类型检查器看的import

```python
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    # 这些import只在mypy检查时执行，运行时不会执行
    # 用于避免循环导入，同时满足类型注解需求
    from myapp.database import Database

class User:
    def __init__(self, db: "Database"):  # 用字符串前向引用
        self._db = db
```

`TYPE_CHECKING`在运行时为`False`，所以`if`块内的import不会执行，避免循环导入。但mypy等类型检查器在静态分析时会把它当作`True`，从而能正确解析类型注解。

#### 第4节 依赖管理：pip、poetry、uv三选一

##### 4.1 三代依赖管理工具

| 特性 | pip | poetry | uv |
|------|-----|--------|-----|
| 语言 | Python | Python | Rust |
| 速度基准 | 1x | ~1x | 10-100x |
| 依赖解析算法 | 回溯 | 回溯 | PubGrub |
| 锁文件 | 无（requirements.txt手动） | `poetry.lock` | `uv.lock` |
| 虚拟环境 | 需配合venv | 内置 | 内置 |
| Python版本管理 | 不支持 | 不支持 | 内置 |
| PEP 621支持 | 间接（通过后端） | v2.0+ | 原生 |
| 发布年份 | 2008 | 2018 | 2024 |

##### 4.2 uv：Rust驱动的"Python的Cargo"

uv由Astral团队（Ruff的创造者）开发，用Rust编写，目标是成为"Python的Cargo"——一个统一的、极快的、可靠的包和项目管理器。[^uv-astral]

```bash
# 安装uv
curl -LsSf https://astral.sh/uv/install.sh | sh

# 创建项目（默认src layout）
uv init myproject
cd myproject

# 添加依赖
uv add fastapi pydantic
uv add --group dev pytest mypy ruff  # 开发依赖组

# 同步环境（创建.venv + 安装所有依赖）
uv sync

# 运行命令（自动使用项目环境）
uv run python -m myapp
uv run pytest
uv run mypy src/

# 锁定依赖
uv lock

# 安装指定Python版本
uv python install 3.12
uv python pin 3.12  # 固定项目Python版本
```

uv的速度优势来自：

- **Rust实现**：无GIL限制，原生并行
- **PubGrub算法**：比传统回溯解析快数个数量级
- **全局缓存**：依赖包只下载一次，所有项目共享（Copy-on-Write + 硬链接）
- **静态二进制**：不依赖Python运行时，冷启动极快

> ⚡ 实测对比：安装Trio依赖（含传递依赖），pip冷启动约15秒，uv冷启动约1秒。热缓存下pip约8秒，uv约0.1秒——快80-115倍。[^uv-benchmark]

##### 4.3 poetry：成熟稳定的选择

```bash
# 创建项目
poetry new myproject
cd myproject

# 添加依赖
poetry add fastapi
poetry add --group dev pytest

# 安装
poetry install

# 运行
poetry run pytest
```

poetry的优势是生态成熟、文档完善、社区活跃。但它是Python写的，速度和pip在同一量级。Poetry 2.0（2025年1月发布）开始支持PEP 621的`[project]`表，但仍然兼容旧的`[tool.poetry]`格式。[^poetry-2-pep621]

##### 4.4 选择建议

- **新项目**：首选`uv`——速度碾压、功能全面、PEP 621原生支持
- **已有poetry项目**：暂不急于迁移，poetry 2.0已支持PEP 621
- **已有pip项目**：可以用`uv pip install`作为pip的直接替代，零迁移成本
- **企业内网环境**：确认镜像源支持后再选择

#### 第5节 性能贴士

| 操作 | Maven | pip | uv |
|------|-------|-----|-----|
| 全新安装10个依赖 | 15-30s | 3-5s | 0.3-0.5s |
| import 100个模块 | N/A | 200-500ms | 同左（import是Python运行时行为，与包管理器无关） |
| 冷启动加载项目 | 3-10s(JVM) | 0.1-0.5s | 0.1-0.5s |
| 创建虚拟环境 | N/A | 1-2s（python -m venv） | 0.01s |

> ⚡ Python的`import`是运行时执行的——大型项目首次启动会有明显的import开销。优化方案：延迟导入（在函数内import非必要模块），或使用`python -X importtime`分析import耗时。Maven项目冷启动主要是JVM启动开销，Python项目冷启动主要是import开销——两者都是"启动税"，只是来源不同。

#### 本章小结

Python项目结构比Maven简洁——没有`src/main/java`的深层嵌套，但src layout是现代最佳实践，强制安装后才能import，提前暴露打包问题。`pyproject.toml`（PEP 621）是Python版的`pom.xml`，工具无关、声明式、一个文件管所有。`import`是运行时执行——理解这一点是避开循环导入陷阱的关键。依赖管理方面，`uv`用Rust重写了整个工具链，比pip快10-100倍，是新项目的首选。

Java的工程化是"框架强制约束"，Python的工程化是"约定自觉遵守"——但约定本身已经收敛到最佳实践，遵循约定比自创结构更省心。

[^pypa-src-layout]: Python Packaging Authority, "src layout vs flat layout", PyPA Packaging Guide, https://packaging.python.org/en/latest/discussions/src-layout-vs-flat-layout/ — "The src layout helps prevent accidental usage of the in-development copy of the code."

[^pydevtools-src-layout]: Tim Hopper, "src layout vs flat layout: which to use and why", PyDevTools Handbook, https://pydevtools.com/handbook/explanation/src-layout-vs-flat-layout — "uv 0.12.0 changed the default from the flat layout to the src layout."

[^pep621-backends]: Tim Hopper, "What is PEP 621?", PyDevTools Handbook, https://pydevtools.com/handbook/explanation/what-is-pep-621-compatibility/ — 列出支持PEP 621的后端：Hatchling(原生)、flit_core(原生)、setuptools(v61+)、pdm-backend(原生)、poetry-core(v2.0+)、uv_build(原生)。

[^uv-astral]: Astral, "uv: Python packaging in Rust", GitHub, https://github.com/astral-sh/uv — "uv is an extremely fast Python package installer and resolver, written in Rust. 10-100x faster than pip and pip-tools."

[^uv-benchmark]: Ben Frederickson, "uv: Python packaging in Rust", Astral Blog, 2024-02-15, https://astral.sh/blog/uv — "In benchmarks, uv is 8-10x faster than pip without cache, and 80-115x faster with warm cache."

[^poetry-2-pep621]: Poetry Documentation, "Migration to PEP 621", https://python-poetry.org/blog/announcing-poetry-2-0-0/ — Poetry 2.0（2025年1月5日发布）开始支持PEP 621的`[project]`表，同时保持对`[tool.poetry]`旧格式的兼容。
