#### 开篇：快递打包的哲学

Java老兵对交付流程再熟悉不过：Maven编译→打包fat jar→java -jar运行。这条链路是"全家桶"式的——一个jar文件包含了所有依赖，丢到任何装了JVM的机器上就能跑。这像快递公司的"整箱发货"：一个箱子装完所有东西，收件人只要有仓库（JVM）就能接收。

Python的交付哲学截然不同。Python不打包依赖到产物里——wheel文件只包含你自己的代码，依赖在安装时从PyPI拉取。这像"零件发货"：你只寄出自己生产的零件，标准件（依赖）让收件人在本地五金店（PyPI）购买。

两种哲学各有优劣。Java的fat jar是"自包含"的——部署简单，不依赖外部仓库，但体积庞大（动辄100-200MB）。Python的wheel是"轻量"的——产物只有几KB到几十KB，但部署时需要网络访问PyPI，且依赖版本可能漂移。

Docker的出现让这场哲学之争有了新的战场。在容器化场景下，Python的轻量优势被放大——镜像小5倍、构建快3倍、冷启动快20倍。这就是为什么AWS Lambda、Google Cloud Run等Serverless平台上Python远比Java流行。

> 💡 比喻：Java的fat jar像整车运输——发动机、轮胎、座椅全装好，到地方就能开，但运费贵、油耗高。Python的wheel像CKD散件运输（Completely Knocked Down，全散装组装）——只运核心部件，标准件到目的地产地采购，运费便宜但需要当地有供应链。Docker则是集装箱——不管你运整车还是散件，都装进标准集装箱里，运输方式统一。

#### 第1节 构建标准：从setup.py到PEP 517/518

##### 1.1 Python构建的"黑暗时代"

在2016年之前，Python的构建被`setup.py`垄断。每个Python包都有一个`setup.py`文件——它是一个可执行的Python脚本，导入setuptools（或更老的distutils），调用`setup()`函数声明元数据和构建逻辑。

这套方案有一个致命的"鸡生蛋"问题：要执行`setup.py`，你必须先知道它需要哪些构建依赖；但要知道构建依赖，你必须执行`setup.py`。pip只能假设所有项目都依赖setuptools，硬编码安装它——这让setuptools成了事实垄断，其他构建工具无法生存[^pep-518]。

```python
# setup.py —— 2016年前的Python构建方式（可执行脚本）
from setuptools import setup, find_packages

setup(
    name="myapp",
    version="1.0.0",
    packages=find_packages(),
    install_requires=[
        "fastapi>=0.104",
        "pydantic>=2.0",
    ],
)
# 问题：pip必须先安装setuptools才能执行这个文件
# 问题：执行Python代码来读取元数据，有安全风险
```

对比Java，Maven从未有过这个问题——`pom.xml`是声明式的XML文件，不需要执行任何代码就能读取构建配置。Python花了十年才走到同一起跑线。

##### 1.2 PEP 518（2016）：pyproject.toml的诞生

2016年，PEP 518引入了`pyproject.toml`文件和`[build-system]`表，用声明式TOML替代可执行的`setup.py`[^pep-518]。pip可以静态读取`[build-system].requires`，在隔离环境中安装构建依赖，再执行构建——打破了"鸡生蛋"循环。

```toml
# pyproject.toml —— PEP 518定义的构建系统声明
[build-system]
requires = ["setuptools>=61", "wheel"]  # 构建依赖（pip在隔离环境中安装）
build-backend = "setuptools.build_meta"  # 构建后端入口
```

PEP 518选择TOML格式，而非JSON或YAML。PEP 518的作者Brett Cannon在PEP中解释了原因：TOML对人类友好（不像JSON）、足够灵活（不像configparser）、源自标准（不像configparser）、不会过度复杂（不像YAML）。Rust社区的Cargo包管理器已经成功使用TOML，证明了它的适用性[^pep-518-format]。

##### 1.3 PEP 517（2017）：构建后端接口

2017年，PEP 517定义了构建前端（frontend）和构建后端（backend）之间的标准接口[^pep-517]。任何工具只要实现了PEP 517的hook函数，就能作为构建后端——setuptools不再是唯一选择。

PEP 517定义的核心hook：

| Hook | 作用 | 必需性 |
|------|------|--------|
| `build_wheel()` | 构建wheel（二进制分发包） | 必需 |
| `build_sdist()` | 构建sdist（源码分发包） | 必需 |
| `get_requires_for_build_wheel()` | 声明额外构建依赖 | 可选 |
| `prepare_metadata_for_build_wheel()` | 提取元数据（不构建完整wheel） | 可选 |

```
构建前端（pip/uv/build）  ──调用hook──>  构建后端（setuptools/hatchling/flit）
     读取pyproject.toml                  实现PEP 517接口
     创建隔离环境                         产出wheel/sdist
     安装构建依赖                         ↑
          ↓                               │
          └───────── 隔离环境 ────────────┘
```

pip 10.0（2018年4月）是第一个支持`[build-system].requires`的安装器。pip 19.0（2019年1月）完整支持PEP 517 hook API。pip 21.3（2021年10月）加入PEP 660（可编辑安装）支持[^pep-517-timeline]。

> 💡 比喻：PEP 517/518之前，Python构建像"全科诊所"——setuptools包揽一切，不管你什么需求都只能找它。PEP 517/518之后，Python构建像"专科医院"——setuptools、hatchling、flit、poetry-core各有所长，你按需选择，pip/uv作为"导诊台"帮你对接。Java的Maven一直是"专科医院"——`pom.xml`声明构建配置，各种plugin各司其职。

##### 1.4 构建后端选型

PEP 517让构建后端成为可替换组件。选择后端只需改`[build-system]`，`[project]`表不变：

| 构建后端 | `build-backend`值 | 适用场景 | 特点 |
|---------|-------------------|---------|------|
| Hatchling | `hatchling.build` | 新项目、纯Python库/应用 | 功能全面，Hatch生态默认 |
| flit_core | `flit_core.buildapi` | 极简纯Python库 | 不支持C扩展，最少配置 |
| setuptools | `setuptools.build_meta` | 遗留项目、最大兼容性 | 老牌工具，支持最全面 |
| poetry-core | `poetry.core.masonry.api` | Poetry生态项目 | 同时支持PEP 621和旧格式 |
| uv_build | `uv.build` | uv生态项目 | 2024年新增，与uv深度集成 |
| maturin | `maturin` | Rust扩展模块 | Cargo+Python混合项目 |
| scikit-build-core | `scikit_build_core.build` | C/C++扩展模块 | 基于CMake，替代旧numpy.distutils |

```toml
# 切换后端只需改这两行，[project]表完全不变
[build-system]
requires = ["hatchling>=1.26"]
build-backend = "hatchling.build"

# 改用flit_core：
# [build-system]
# requires = ["flit_core>=3.8"]
# build-backend = "flit_core.buildapi"
```

#### 第2节 打包格式：wheel vs jar/war

##### 2.1 产物对比

| 维度 | Java（jar/war） | Python（wheel） | 差异本质 |
|------|----------------|----------------|----------|
| 格式 | ZIP压缩包 | ZIP压缩包（.whl扩展名） | 本质相同 |
| 包含依赖 | fat jar包含全部 | 不包含，安装时拉取 | 哲学差异 |
| 典型大小 | 50-200MB（fat jar） | 10-50KB（纯Python） | 100-1000x |
| 运行方式 | `java -jar app.jar` | `python -m myapp` | 需要解释器 |
| 编译产物 | .class字节码 | 可选.pyc缓存 | 都是中间码 |
| 平台相关性 | 跨平台（JVM抽象） | 可标记平台标签 | wheel更精确 |

##### 2.2 wheel文件名的秘密

wheel文件名遵循标准格式，编码了兼容性信息：

```
myapp-1.0.0-cp312-cp312-manylinux2014_x86_64.whl
└──┬─┘ └──┬─┘ └─┬──┘ └─┬──┘ └──────┬───────┘
  包名     版本    实现    ABI       平台标签
```

| 标签 | 含义 | 示例 |
|------|------|------|
| `cp312` | CPython 3.12 | 实现版本+Python版本 |
| `cp312` (ABI) | CPython 3.12 ABI | 二进制兼容性 |
| `manylinux2014_x86_64` | manylinux 2014标准, x86_64架构 | Linux平台兼容性 |
| `py3-none-any` | 纯Python 3，任意平台 | 纯Python包最通用 |

```bash
# 构建wheel
python -m build --wheel
# 或用uv
uv build --wheel

# 产出：dist/myapp-1.0.0-py3-none-any.whl
```

Java的jar文件名没有这种精确的兼容性编码——因为JVM的"一次编写，到处运行"承诺让jar天然跨平台。Python的wheel需要精确标记平台，因为C扩展模块（如NumPy）是平台相关的。

##### 2.3 sdist vs wheel

Python有两种分发格式：

| 格式 | 内容 | 适用场景 |
|------|------|---------|
| sdist（源码分发） | 源码+构建配置 | wheel不可用时的后备 |
| wheel（二进制分发） | 预构建产物 | 首选，安装快 |

```bash
# 同时构建sdist和wheel
python -m build
# 产出：
# dist/myapp-1.0.0.tar.gz  (sdist)
# dist/myapp-1.0.0-py3-none-any.whl  (wheel)
```

> 💡 比喻：sdist像"图纸+零件清单"——你需要自己加工组装。wheel像"预制模块"——拆箱即用。pip优先安装wheel，没有wheel才回退到sdist（需要本地编译）。Java的jar更像wheel——已经是编译好的.class文件，不需要源码。

#### 第3节 Docker镜像：Java重卡 vs Python自行车

##### 3.1 镜像大小对比

```dockerfile
# Java Spring Boot镜像——通常300-500MB
FROM openjdk:17-slim
COPY app.jar /app.jar
ENTRYPOINT ["java", "-jar", "/app.jar"]

# Python slim镜像——通常50-100MB
FROM python:3.12-slim
COPY . /app
RUN pip install -r requirements.txt
ENTRYPOINT ["python", "/app/main.py"]
```

| 指标 | Spring Boot镜像 | Python slim镜像 | 倍数 |
|------|----------------|----------------|------|
| 基础镜像 | openjdk:17-slim ~400MB | python:3.12-slim ~45MB | 9x |
| 应用层 | fat jar 50-200MB | 源码+依赖 5-50MB | 4-10x |
| 总镜像大小 | 300-500MB | 50-100MB | 5-6x |
| 构建时间 | 60-120s | 15-30s | 3-4x |
| 冷启动 | 3-10s（JVM启动） | 0.1-0.5s | 20-50x |

> ⚡ Python在容器化/Serverless场景下的优势：镜像小5倍、构建快3倍、冷启动快20倍。这就是为什么AWS Lambda/Google Cloud Run上Python远比Java流行——Serverless按启动时间计费，JVM的3-10秒冷启动是致命的。

##### 3.2 多阶段构建：Python的层缓存优化

Java的Docker构建相对简单——Maven已经把依赖打进fat jar，COPY一个文件即可。Python需要更精细的多阶段构建来利用层缓存：

```dockerfile
# Python多阶段构建——优化层缓存

# === 阶段1: 构建阶段 ===
FROM python:3.12-slim AS builder

# 安装uv（比pip快10-100x）
COPY --from=ghcr.io/astral-sh/uv:latest /uv /bin/uv

# 先COPY依赖文件（利用层缓存）
WORKDIR /app
COPY pyproject.toml uv.lock ./

# 安装依赖到.venv（这一层会在依赖不变时缓存）
RUN uv sync --frozen --no-install-project

# 再COPY源码（源码变更不会使依赖层缓存失效）
COPY src/ ./src/

# 安装项目本身
RUN uv sync --frozen

# === 阶段2: 运行阶段 ===
FROM python:3.12-slim AS runtime

# 创建非root用户
RUN useradd --create-home appuser
WORKDIR /home/appuser/app

# 从构建阶段复制.venv（不包含构建工具）
COPY --from=builder --chown=appuser:appuser /app/.venv ./.venv
COPY --from=builder --chown=appuser:appuser /app/src ./src

# 切换到非root用户
USER appuser

# 使用.venv中的Python
ENTRYPOINT ["/home/appuser/app/.venv/bin/python", "-m", "myapp"]
```

层缓存的关键原理：Docker按Dockerfile指令顺序构建镜像层，某一层变更会使后续所有层缓存失效。因此：

1. **先COPY依赖声明文件**（`pyproject.toml`、`uv.lock`）→ 依赖不变时这层缓存命中
2. **安装依赖**（`RUN uv sync`）→ 依赖不变时这层缓存命中
3. **后COPY源码** → 源码变更只使这层及后续失效，依赖层不受影响

```dockerfile
# ❌ 错误写法：COPY全部内容再安装依赖
COPY . .                    # 源码变更导致这层缓存失效
RUN pip install -e .        # 依赖层也失效，每次都要重新安装全部依赖

# ✅ 正确写法：分离依赖声明和源码
COPY pyproject.toml uv.lock ./  # 依赖声明单独一层
RUN uv sync --frozen            # 依赖安装层，源码变更不影响
COPY src/ ./src/                # 源码单独一层
```

##### 3.3 Java的Docker构建对比

```dockerfile
# Java多阶段构建
FROM maven:3.9-eclipse-temurin-17 AS builder
WORKDIR /app
# 先COPY pom.xml，下载依赖（利用层缓存）
COPY pom.xml .
RUN mvn dependency:go-offline
# 再COPY源码
COPY src/ ./src/
RUN mvn package -DskipTests

FROM eclipse-temurin:17-jre-alpine
COPY --from=builder /app/target/app.jar /app.jar
ENTRYPOINT ["java", "-jar", "/app.jar"]
```

两者都用"先COPY依赖声明，后COPY源码"的策略。差异在于：

| 维度 | Java | Python |
|------|------|--------|
| 依赖层缓存对象 | Maven本地仓库（~/.m2） | .venv虚拟环境 |
| 运行阶段体积 | JRE ~180MB + jar | Python ~45MB + .venv |
| 构建工具残留 | 不需要Maven（fat jar自包含） | 不需要pip/uv（.venv已安装好） |
| 分层粒度 | 粗（一个jar） | 细（.venv中每个包独立） |

##### 3.4 .dockerignore：容易被遗忘的优化

```
# .dockerignore —— 防止不必要文件进入构建上下文
.git
.gitignore
.venv
__pycache__
*.pyc
.pytest_cache
.mypy_cache
.ruff_cache
tests/
docs/
*.md
.env
```

没有`.dockerignore`，Docker会把整个项目目录发送到daemon作为构建上下文。对于Python项目，`.venv`目录可能包含数百MB的包——如果不忽略，每次`docker build`都会传输这些无用文件，严重拖慢构建。

Java项目同样需要`.dockerignore`，但影响较小——Maven的`target/`目录通常只有编译产物，不像Python的`.venv`那样庞大。

#### 第4节 依赖锁定：uv.lock vs poetry.lock vs Maven

##### 4.1 为什么需要锁定？

Maven的依赖解析是确定性的——`pom.xml`声明版本范围，但Maven会用最近定义原则（nearest definition）解析冲突，同一份`pom.xml`在不同时间构建可能得到不同的依赖树（如果传递依赖发布了新版本）。

Maven通过`mvn dependency:tree`查看依赖树，但不会自动生成锁定文件。要实现可复现构建，Java项目通常用`mvn versions:lock-snapshots`或Gradle的`gradle.lockfile`。

Python的依赖锁定更成熟——主流工具都支持生成锁文件：

| 工具 | 锁文件 | 格式 | 可移植性 |
|------|--------|------|---------|
| uv | `uv.lock` | TOML | 跨平台 |
| poetry | `poetry.lock` | TOML | 跨平台 |
| pip-tools | `requirements.txt` | 纯文本 | 平台相关 |
| pdm | `pdm.lock` | TOML | 跨平台 |
| Maven | 无标准锁文件 | — | — |
| Gradle | `gradle.lockfile` | 纯文本 | 跨平台 |

##### 4.2 uv.lock：现代依赖锁定

uv由Astral公司（Ruff的创造者）开发，用Rust编写，2024年2月15日发布[^uv-release]。uv的目标是成为"Python的Cargo"——一个统一的、极快的、可靠的包和项目管理器[^uv-astral]。

```bash
# uv工作流
uv init myproject           # 创建项目（默认src layout）
cd myproject
uv add fastapi pydantic     # 添加依赖（自动更新pyproject.toml和uv.lock）
uv add --group dev pytest mypy ruff  # 开发依赖组
uv lock                     # 重新锁定依赖
uv sync                     # 按uv.lock精确安装到.venv
uv run python -m myapp      # 在项目环境中运行
```

```toml
# uv.lock（简化示例）—— 跨平台锁文件
[[package]]
name = "fastapi"
version = "0.104.1"
source = { registry = "https://pypi.org/simple" }
dependencies = [
    { name = "starlette", version = ">=0.27.0,<0.28.0" },
    { name = "pydantic", version = ">=1.7.4" },
]

[[package]]
name = "starlette"
version = "0.27.0"
source = { registry = "https://pypi.org/simple" }
```

uv的速度优势来自四个方面：

| 技术手段 | 效果 | 对比pip |
|---------|------|---------|
| Rust实现 | 无GIL限制，原生并行 | pip受GIL限制 |
| PubGrub算法 | 比回溯解析快数个数量级 | pip用回溯算法 |
| 全局缓存 | 依赖包只下载一次，硬链接复用 | pip每个环境独立下载 |
| 静态二进制 | 不依赖Python运行时，冷启动极快 | pip需要Python运行时 |

> ⚡ 实测对比：安装Trio依赖（含传递依赖），pip冷启动约15秒，uv冷启动约1秒。热缓存下pip约8秒，uv约0.1秒——快80-115倍[^uv-benchmark]。

##### 4.3 poetry.lock：成熟稳定的选择

```bash
# poetry工作流
poetry new myproject
cd myproject
poetry add fastapi
poetry add --group dev pytest
poetry lock       # 生成poetry.lock
poetry install    # 按poetry.lock安装
poetry run pytest # 在项目环境中运行
```

poetry的优势是生态成熟、文档完善。Poetry 2.0（2025年1月5日发布）开始支持PEP 621的`[project]`表，同时兼容旧的`[tool.poetry]`格式[^poetry-2-release]。

##### 4.4 uv vs poetry vs Maven对比

| 维度 | Maven | poetry | uv |
|------|-------|--------|-----|
| 语言 | Java | Python | Rust |
| 锁文件 | 无标准 | `poetry.lock` | `uv.lock` |
| 速度 | 中等 | ~1x（基准） | 10-100x |
| 解析算法 | 最近定义 | 回溯 | PubGrub |
| PEP 621 | N/A | v2.0+ | 原生 |
| 虚拟环境 | N/A | 内置 | 内置 |
| Python版本管理 | N/A | 不支持 | 内置 |
| 发布年份 | 2004 | 2018 | 2024 |

> 💡 选择建议：新项目首选`uv`——速度碾压、功能全面、PEP 621原生支持。已有poetry项目暂不急于迁移，poetry 2.0已支持PEP 621。已有pip项目可以用`uv pip install`作为pip的直接替代，零迁移成本。

#### 第5节 CI/CD集成

##### 5.1 GitHub Actions示例

```yaml
# .github/workflows/ci.yml —— Python CI流水线
name: CI

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python-version: ["3.12", "3.13"]
    
    steps:
      - uses: actions/checkout@v4
      
      - name: Install uv
        uses: astral-sh/setup-uv@v3
        with:
          version: "latest"
      
      - name: Set up Python
        run: uv python install ${{ matrix.python-version }}
      
      - name: Install dependencies
        run: uv sync --frozen  # 按uv.lock精确安装
      
      - name: Lint (ruff)
        run: uv run ruff check src/
      
      - name: Type check (mypy)
        run: uv run mypy src/
      
      - name: Test (pytest)
        run: uv run pytest --cov
      
      - name: Build wheel
        run: uv build --wheel
      
      - name: Upload artifact
        uses: actions/upload-artifact@v4
        with:
          name: wheel-${{ matrix.python-version }}
          path: dist/*.whl
```

```yaml
# 对比：Java的Maven CI流水线
name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          java-version: '17'
          distribution: 'temurin'
      - name: Cache Maven
        uses: actions/cache@v4
        with:
          path: ~/.m2
          key: ${{ runner.os }}-m2-${{ hashFiles('**/pom.xml') }}
      - name: Build
        run: mvn -B package
      - name: Upload artifact
        uses: actions/upload-artifact@v4
        with:
          name: jar
          path: target/*.jar
```

两者结构相似，关键差异：

| 维度 | Java (Maven) | Python (uv) |
|------|-------------|-------------|
| 环境准备 | setup-java | setup-uv + uv python install |
| 依赖缓存 | ~/.m2手动缓存 | uv全局缓存自动 |
| 依赖安装 | mvn package（含编译） | uv sync（仅安装） |
| 构建产物 | target/*.jar | dist/*.whl |
| 多版本测试 | 矩阵+不同Java | 矩阵+uv python install |
| CI耗时 | 3-5分钟 | 30-60秒 |

#### 第6节 PEP 723：单文件脚本的依赖声明

2023年，PEP 723引入了"内联脚本元数据"——在单个`.py`文件顶部用注释声明依赖[^pep-723]。这对一次性脚本和自动化任务极其有用，不需要创建完整项目结构。

```python
# fetch_data.py —— 单文件脚本，自带依赖声明
# /// script
# requires-python = ">=3.12"
# dependencies = [
#     "requests>=2.31",
#     "rich>=13.0",
# ]
# ///

import requests
from rich import print

response = requests.get("https://api.github.com/repos/astral-sh/uv")
data = response.json()
print(f"uv stars: [bold]{data['stargazers_count']}[/bold]")
```

```bash
# uv run自动读取内联依赖，创建临时环境，运行脚本，销毁环境
uv run fetch_data.py
# 输出：uv stars: 28000
```

Java没有等价物——Java的单文件脚本（single-file source-code）从Java 11开始支持（`java HelloWorld.java`），但不能声明第三方依赖。PEP 723让Python在"脚本即程序"的便捷性上远超Java。

> 💡 比喻：PEP 723像"自热火锅"——包装里自带加热包，加水就能吃，不需要锅碗瓢盆。传统Python项目像"在家做饭"——需要厨房（虚拟环境）、菜谱（pyproject.toml）、食材清单（requirements.txt）。Java的单文件执行像"泡面"——能快速吃上，但加不了配菜（第三方依赖）。

#### ⚡ 性能贴士

| 操作 | Java (Maven) | Python (pip) | Python (uv) |
|------|-------------|-------------|-------------|
| 全新安装10个依赖 | 15-30s | 3-5s | 0.3-0.5s |
| 增量安装1个依赖 | 5-10s | 1-2s | 0.05-0.1s |
| 创建虚拟环境 | N/A | 1-2s (venv) | 0.01s |
| 构建产物 | 10-30s (mvn package) | 2-5s (build) | 0.5-1s (uv build) |
| Docker构建（冷） | 60-120s | 15-30s | 5-10s |
| Docker构建（缓存） | 15-30s | 5-10s | 1-3s |

**优化建议**：

1. **CI中用uv替代pip**：冷安装从分钟级降到秒级，CI流水线提速3-5倍
2. **Docker用多阶段构建**：运行镜像不含构建工具，体积减小30-50%
3. **Docker层缓存排序**：先COPY依赖声明，后COPY源码，依赖不变时跳过安装
4. **用`.dockerignore`**：排除`.venv`、`__pycache__`等，构建上下文从数百MB降到几MB
5. **用slim基础镜像**：`python:3.12-slim`比`python:3.12`小200MB+
6. **非root用户运行**：`USER appuser`，安全性提升，符合容器最佳实践

> 💡 性能口诀：CI用uv，Docker分阶段，依赖先COPY，slim打底盘。

#### 踩坑日记：Docker镜像里依赖装了又装

> 📝 第一人称踩坑记录

"第一次给Python项目写Dockerfile，我照着Java的习惯写：

```dockerfile
FROM python:3.12
COPY . .
RUN pip install -r requirements.txt
ENTRYPOINT ["python", "main.py"]
```

构建倒是成功了，但镜像有800MB——比Java的fat jar还大。QA反馈说每次改一行代码，Docker构建要3分钟。

我花了半天排查，发现问题出在层缓存：`COPY . .`把全部文件（包括源码）复制进去，然后`RUN pip install`——每次源码变更，这层缓存就失效，pip要重新安装全部依赖。

修改方案：先COPY requirements.txt，安装依赖，再COPY源码：

```dockerfile
FROM python:3.12-slim
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY src/ ./src/
ENTRYPOINT ["python", "src/main.py"]
```

镜像从800MB降到150MB，构建时间从3分钟降到20秒（依赖层缓存命中）。

后来又换了uv + 多阶段构建，最终镜像降到60MB，构建时间5秒。Java老兵在Python世界，每个'常识'都需要重新校准。"

#### 思维实验

> 🤔 思考题：如果Python像Java一样，把依赖打包进wheel（"fat wheel"），会带来什么好处和什么问题？为什么Python社区始终坚持"wheel不含依赖"的设计？

提示：思考以下场景——
- 依赖发现安全漏洞时，fat wheel需要重新构建发布，而当前模式只需更新PyPI上的依赖包
- 多个项目共享同一依赖时，fat wheel各自包含一份（冗余），当前模式全局缓存一份
- Docker镜像中，fat wheel无法利用层缓存分离依赖和源码

#### 本章小结

1. **构建标准化**：PEP 517/518让Python构建从"setup.py垄断"走向"后端可替换" —— 像从全科诊所到专科医院，setuptools/hatchling/flit各司其职
2. **wheel轻量哲学**：Python的wheel只含自己的代码，依赖安装时拉取 —— vs Java fat jar的"自包含"哲学，各有优劣
3. **Docker轻量优势**：Python slim镜像比Spring Boot镜像小5倍、冷启动快20倍 —— Serverless场景的杀手锏
4. **uv改变游戏**：Rust实现的uv比pip快10-100x，一个工具替代pip/pip-tools/pipx/poetry/pyenv/virtualenv —— Python的Cargo
5. **依赖锁定成熟**：uv.lock/poetry.lock提供跨平台可复现构建 —— 比Maven的"无标准锁文件"更完善
