### 第18章 类型注解与静态检查：给动态类型加上安全带

> 📖 本章你将学会：
> - 用 Type Hints 为 Python 代码标注类型，获得 IDE 智能补全和文档化收益
> - 用 mypy 或 pyright 执行编译期类型检查，在 CI 中拦截类型错误
> - 用 Protocol + 泛型实现"鸭子接口"，在不继承的前提下获得类型安全
> - 理解 Python 类型系统的演进脉络，从 PEP 484 到 PEP 695

---

#### 开篇：自愿安检的哲学

Java 程序员对安检门习以为常——每个变量、每个参数、每个返回值，编译器都要过一遍检查。你不写类型？编译不过。这像机场安检：每个包裹必须过机，慢但安全。

Python 的世界截然不同。2014 年之前，Python 没有任何类型标注的标准语法——函数参数可以传任何东西，返回值可以是任何类型，运行时才发现 `TypeError`。这像地铁站：直接冲进去，出事了再说。

2014 年 9 月，Guido van Rossum 在 PEP 484 中提出了 Type Hints（类型提示）的标准化方案[^pep-484]。但关键是——Python 的类型注解是**自愿安检**：你可以选择走安检（用 mypy/pyright 检查），也可以直接冲过去（运行时报错）。Python 解释器在运行时**忽略**类型注解，不做任何检查。类型安全由独立的离线工具（mypy、pyright）提供。

> 💡 比喻：Java 的类型系统像机场安检门——每个包裹过机检查，慢但安全，不检查不让上飞机。Python 的类型注解像地铁站的自愿安检——你可以走安检通道（mypy 检查），也可以直接上车（运行时报错）。Python 给你选择权，但选择权也意味着责任。

#### Java 回顾

Java 的类型系统是编译期强制的：

```java
// Java: 编译器在编译期检查所有类型
public String process(User user) {
    return user.getName();  // 编译器知道 user 是 User 类型
}

// 类型不匹配 → 编译报错
String result = process(42);  // error: incompatible types
```

Java 的类型检查有三个特点：

1. **编译期强制**：不写类型、类型不匹配 → 编译失败
2. **运行时类型擦除**：泛型 `List<String>` 在运行时变成裸 `List`（类型擦除）
3. **名义子类型**（nominal subtyping）：`A extends B` 才算子类型，结构相同不算

> 💡 提示：如果你对 Java 泛型类型擦除已经很熟悉，可以跳过本节直接看下一节。

#### Python 视角

Python 的类型注解系统从 2015 年的 PEP 484（Python 3.5）开始，经历了一系列 PEP 演进，到 Python 3.12 的 PEP 695 形成了完整体系。下面按时间线梳理关键里程碑。

##### 18.1 类型注解演进时间线

| PEP | 版本 | 语法特性 | 作者 | 核心价值 |
|-----|------|---------|------|---------|
| PEP 3107 | 3.0 | 函数注解语法 `def f(x: int)` | Collin Winter 等 | 语法基础，语义未定义 |
| PEP 484 | 3.5 | Type Hints 标准化 + `typing` 模块 | Guido van Rossum 等 | 类型系统正式确立 |
| PEP 526 | 3.6 | 变量注解 `x: int = 1` | Ryan Gonzalez 等 | 变量也能标注类型 |
| PEP 544 | 3.8 | Protocol 结构化子类型 | Ivan Levkivskyi 等 | 鸭子类型 + 静态检查 |
| PEP 604 | 3.10 | `X \| Y` 联合类型语法 | Philip House | 替代 `Union[X, Y]` |
| PEP 695 | 3.12 | `class C[T]:` 泛型新语法 + `type` 语句 | Eric Traut | 泛型语法糖，告别 TypeVar |

[^pep-484]: PEP 484: Type Hints, Guido van Rossum, Jukka Lehtosalo, Łukasz Langa, 2014-09-29, https://peps.python.org/pep-0484/ — Python 3.5 引入，`typing` 模块在 3.7 前为 provisional（暂定）状态，3.7 正式稳定。

[^pep-526]: PEP 526: Syntax for Variable Annotations, Ryan Gonzalez, Philip House, Ivan Levkivskyi, Lisa Roach, Guido van Rossum, 2016-09-02, https://peps.python.org/pep-0526/ — Python 3.6 引入变量注解语法，此前只能用 `# type: int` 注释。

[^pep-544]: PEP 544: Protocols – Structural subtyping (static duck typing), Ivan Levkivskyi, Jukka Lehtosalo, Łukasz Langa, 2017-03-05, https://peps.python.org/pep-0544/ — Python 3.8 引入，实现了结构化子类型（structural subtyping），即静态鸭子类型。

[^pep-604]: PEP 604: Allow writing union types as X \| Y, Philip House, 2019-08-06, https://peps.python.org/pep-0604/ — Python 3.10 引入 `X | Y` 联合类型语法，可替代 `Union[X, Y]` 和 `Optional[X]`（用 `X | None`）。

[^pep-695]: PEP 695: Type Parameter Syntax, Eric Traut, 2023-04-04, https://peps.python.org/pep-0695/ — Python 3.12 引入 `class C[T]:`、`def f[T]():`、`type Alias = ...` 新语法，无需显式声明 `TypeVar` 和 `Generic[T]`，方差自动推断。

##### 18.2 基础注解语法

```python
# Python 3.5+ (PEP 484): 函数参数和返回值注解
def greet(name: str) -> str:
    return f"Hello, {name}"

# Python 3.6+ (PEP 526): 变量注解
count: int = 0
users: list[str] = []  # Python 3.9+ 可用 list[str]，之前需 typing.List[str]

# Python 3.10+ (PEP 604): 联合类型用 | 语法
def parse(value: str | int | float) -> str:  # 等价于 Union[str, int, float]
    return str(value)

# Optional 也可用 | None 替代
def find(id: int) -> str | None:  # 等价于 Optional[str]
    return database.get(id)
```

```java
// Java 等价写法
public String greet(String name) {
    return "Hello, " + name;
}

// Java 没有联合类型，只能用方法重载或 Object
public String parse(Object value) {
    return String.valueOf(value);
}
```

**关键差异解读**：
- **联合类型**：Python 的 `str | int` 是真正的联合类型，mypy 能精确检查。Java 没有联合类型，只能用重载或 `Object`（失去类型安全）。
- **Optional**：Python 的 `str | None` 对应 Java 的 `Optional<String>`，但 Python 的 `None` 是一等公民，不需要包装类。

##### 18.3 泛型：从 TypeVar 到 PEP 695

Python 泛型经历了两个阶段：

**Python 3.5 – 3.11：TypeVar + Generic（冗长但通用）**

```python
# Python 3.5+ (PEP 484): 泛型函数
from typing import TypeVar, Sequence

T = TypeVar('T')  # 声明类型变量
def first(items: Sequence[T]) -> T:
    return items[0]

# 泛型类
from typing import Generic
class Stack(Generic[T]):
    def __init__(self) -> None:
        self._items: list[T] = []
    def push(self, item: T) -> None:
        self._items.append(item)
    def pop(self) -> T:
        return self._items.pop()
```

```java
// Java 等价写法
public class Stack<T> {
    private List<T> items = new ArrayList<>();
    public void push(T item) { items.add(item); }
    public T pop() { return items.remove(items.size() - 1); }
}
```

**Python 3.12+（PEP 695）：新语法（简洁且更安全）**

```python
# Python 3.12+ (PEP 695): 泛型新语法——无需 TypeVar 和 Generic
def first[T](items: Sequence[T]) -> T:
    return items[0]

class Stack[T]:
    def __init__(self) -> None:
        self._items: list[T] = []
    def push(self, item: T) -> None:
        self._items.append(item)
    def pop(self) -> T:
        return self._items.pop()

# type 语句：类型别名
type Point = tuple[float, float]
type Maybe[T] = T | None  # 泛型类型别名
```

PEP 695 新语法相比旧语法的改进：

| 维度 | 旧语法（TypeVar + Generic） | 新语法（PEP 695） | 差异本质 |
|------|---------------------------|------------------|----------|
| 声明量 | 需要额外声明 `T = TypeVar('T')` | 直接在 `[]` 中声明 | 减少样板代码 |
| 作用域 | TypeVar 是模块级变量，全局可见 | 类型参数限定在类/函数作用域内 | 避免命名污染 |
| 方差 | 需手动声明 `covariant=True` | 自动推断方差 | 减少人为错误 |
| 运行时 | `TypeVar` 对象存在 | 可通过 `C.type_params` 内省 | 更好的可检查性 |

> ⚠️ 注意：PEP 695 语法是 Python 3.12 的**语法**特性，`typing_extensions` 无法向后移植。如果项目需要支持 3.11 及以下，只能用旧语法。

##### 18.4 Protocol：静态鸭子类型

PEP 544 引入的 `Protocol` 是 Python 类型系统中最让 Java 程序员兴奋的特性——它实现了**结构化子类型**（structural subtyping），即"静态鸭子类型"。

```python
# Python 3.8+ (PEP 544): Protocol 定义
from typing import Protocol

class SupportsClose(Protocol):
    def close(self) -> None: ...

# 任何有 close() 方法的类都自动满足 SupportsClose，无需继承
class FileResource:
    def close(self) -> None:
        print("closing file")

class NetworkResource:
    def close(self) -> None:
        print("closing socket")

def close_all(resources: list[SupportsClose]) -> None:
    for r in resources:
        r.close()

close_all([FileResource(), NetworkResource()])  # ✅ 类型检查通过
close_all([1, 2, 3])  # ❌ mypy 报错：int 没有 close 方法
```

```java
// Java 等价写法：必须显式 implements
public interface Closeable {
    void close();
}

public class FileResource implements Closeable {  // 必须显式声明
    public void close() { System.out.println("closing file"); }
}

// 如果 FileResource 没写 implements Closeable，即使有 close() 方法也不能用
```

**Protocol vs Java Interface 的核心差异**：

| 维度 | Java Interface | Python Protocol | 差异本质 |
|------|---------------|----------------|----------|
| 子类型关系 | 名义子类型（nominal） | 结构子类型（structural） | 是否需要显式声明 |
| 第三方类适配 | 必须修改源码加 `implements` | 无需修改，自动适配 | 对遗留代码友好 |
| 运行时检查 | `instanceof` 可靠 | `isinstance` 需 `@runtime_checkable` | 检查精度不同 |
| 默认实现 | Java 8+ 有 `default` 方法 | Protocol 可有默认实现 | 能力相当 |
| 多继承 | 接口可多继承 | Protocol 可多继承 | 能力相当 |

> 💡 比喻：Java Interface 像正式合同——双方签字（`implements`）才算生效。Python Protocol 像默契约定——只要你的行为符合（有相同方法），就算你同意了，不需要签字。这让 Python 在处理第三方库时极其灵活。

##### 18.5 TypedDict：字典的类型安全

```python
# Python 3.8+ (PEP 589): TypedDict 给字典加类型
from typing import TypedDict

class UserInfo(TypedDict):
    name: str
    age: int
    email: str | None

# mypy 会检查键和值的类型
user: UserInfo = {"name": "Alice", "age": 30, "email": None}  # ✅
user = {"name": "Alice", "age": "thirty"}  # ❌ mypy 报错：age 应为 int
```

```java
// Java 等价：用 record 或 POJO
public record UserInfo(String name, int age, String email) {}
```

TypedDict 的价值在于：处理 JSON / API 响应时，不需要定义完整的类，用字典就能获得类型安全。这在数据处理场景中极其常用。

#### 代码实战

**场景描述**：构建一个类型安全的仓储模式（Repository Pattern），支持泛型实体和 Protocol 接口。

```python
# Python 3.12 实现（PEP 695 语法）
from typing import Protocol

# 定义实体协议——任何有 id 属性的对象都可满足
class Entity(Protocol):
    id: int

# 泛型仓储——PEP 695 新语法
class Repository[T: Entity]:
    def __init__(self) -> None:
        self._store: dict[int, T] = {}

    def save(self, entity: T) -> None:
        self._store[entity.id] = entity

    def find(self, id: int) -> T | None:
        return self._store.get(id)

    def find_all(self) -> list[T]:
        return list(self._store.values())

# 具体实体——无需继承 Entity
class User:
    def __init__(self, id: int, name: str) -> None:
        self.id = id
        self.name = name

class Product:
    def __init__(self, id: int, price: float) -> None:
        self.id = id
        self.price = price

# 使用
user_repo: Repository[User] = Repository()
user_repo.save(User(1, "Alice"))
user_repo.save(User(2, "Bob"))
found = user_repo.find(1)
if found:
    print(found.name)  # IDE 补全 .name

product_repo: Repository[Product] = Repository()
product_repo.save(Product(101, 29.99))
product = product_repo.find(101)
if product:
    print(product.price)  # IDE 补全 .price

# mypy 检查：
# user_repo.save(Product(1, 9.99))  # ❌ 错误：Product 不能存入 Repository[User]
```

```java
// Java 等价实现
public interface Entity {
    int getId();
}

public class UserRepository implements Repository<User> { ... }

// Java 的 Repository<User> 只能存 User，因为 User 必须 implements Entity
// 如果 User 类是第三方库的，无法修改源码加 implements，就无法适配
```

**关键差异解读**：
- **Protocol 自动适配**：Python 的 `User` 和 `Product` 不需要 `implements Entity`，只要有 `id` 属性就自动满足 Protocol。Java 必须显式 `implements`。
- **泛型约束**：PEP 695 的 `class Repository[T: Entity]` 中的 `T: Entity` 是上界约束，等价于 Java 的 `<T extends Entity>`。
- **联合返回**：`T | None` 比 Java 的 `Optional<T>` 更轻量——`None` 直接可用，不需要 `Optional.of()` 包装。

> ⚠️ 注意：Java 程序员最容易踩的坑是以为 `isinstance(obj, Protocol)` 和 Java 的 `instanceof` 一样可靠。Protocol 的运行时检查只验证方法名是否存在，不验证签名。生产代码中优先依赖 mypy 的静态检查。

#### 工具链：mypy vs pyright

Python 的类型检查工具有两大主流选择：

##### 18.6 mypy：元老级类型检查器

mypy 是 PEP 484 的直接灵感来源——PEP 484 的作者之一 Jukka Lehtosalo 正是 mypy 的创始人。mypy 最初是 Dropbox 内部项目，后开源并成为 Python 类型检查的事实标准[^mypy-history]。

[^mypy-history]: Jukka Lehtosalo, "Our journey to type checking 4 million lines of Python", Dropbox Tech Blog, 2019-09-05, https://dropbox.tech/tech/2019/09/our-journey-to-type-checking-4-million-lines-of-python/ — 记录了 mypy 从学术原型到 Dropbox 4 百万行代码库的演进历程。mypy 首个 PyPI 版本发布于 2016-05-05（v0.3.1），1.0 版本于 2023-02-06 发布。

```bash
# 安装
pip install mypy

# 基本检查
mypy myapp/

# 严格模式（推荐团队项目）
mypy --strict myapp/

# 仅检查有注解的代码（渐进式引入）
mypy myapp/
```

##### 18.7 pyright：微软的高性能检查器

pyright 由微软开发，用 TypeScript 编写，2019 年 3 月首次发布[^pyright-release]。它比 mypy 快 5 倍以上，且深度集成 VS Code（通过 Pylance 扩展）。pyright 还能对**未注解**的代码进行类型推断，这对渐进式引入类型非常友好。

[^pyright-release]: Microsoft, "Pyright: Static type checker for Python", GitHub, 2019-03-22, https://github.com/microsoft/pyright — pyright 首个 GitHub Release 于 2019 年 3 月发布。Pylance（基于 pyright 的 VS Code 扩展）于 2020 年 6 月发布。

```bash
# 安装（需要 Node.js）
npm install -g pyright

# 检查
pyright myapp/

# VS Code 用户推荐安装 Pylance 扩展（内置 pyright）
```

##### 18.8 mypy vs pyright 对比

| 维度 | mypy | pyright | 推荐场景 |
|------|------|---------|---------|
| 实现语言 | Python | TypeScript / Node.js | — |
| 检查速度 | 中等 | 快 5x+ | 大型项目选 pyright |
| 未注解代码 | 不检查 | 类型推断，部分检查 | 渐进式引入选 pyright |
| CI 集成 | `pip install mypy` | `npm install -g pyright` | Python 纯环境选 mypy |
| IDE 集成 | 需插件 | VS Code 内置（Pylance） | VS Code 用户选 pyright |
| 社区地位 | PEP 484 灵感来源 | 微软官方支持 | 两者均为主流 |
| 首次发布 | 2016-05 (v0.3.1) | 2019-03 | — |

> 💡 建议：个人开发用 pyright（VS Code 集成好、速度快），CI 流水线可以两者都用——pyright 做快速反馈，mypy 做权威检查。

#### ⚡ 性能贴士

类型注解在运行时的开销是 Java 程序员最关心的问题。答案是：**几乎为零**。

| 操作 | 有注解 | 无注解 | 开销 |
|------|--------|--------|------|
| 函数调用 | ~50ns | ~50ns | 0 |
| 变量赋值 | ~5ns | ~5ns | 0 |
| `__annotations__` 读取 | 首次构建 dict | 无 | 一次性 |
| mypy/pyright 检查 | 离线，不影响运行 | — | CI 时 |

CPython 解释器在执行字节码时**完全忽略**类型注解——注解只是存储在 `__annotations__` 属性中的元数据，不参与运行时逻辑。唯一的例外是使用了 `@dataclass`、Pydantic 等运行时读取注解的装饰器/框架。

```python
# 证明：运行时注解不影响行为
def add(a: int, b: int) -> int:
    return a + b

print(add(1, 2))        # 3
print(add("a", "b"))    # "ab" —— 运行时不报错！
# mypy 会报错，但 Python 解释器不管
```

```java
// Java：编译期就拦截
public int add(int a, int b) { return a + b; }
add("a", "b");  // 编译错误：incompatible types
```

**优化建议**：
1. **团队项目强制 mypy/pyright**：在 CI 中加入 `mypy --strict` 或 `pyright`，像 Java 的 `javac` 一样作为编译门禁
2. **个人脚本可选**：一次性脚本不需要类型注解，但库和长期维护的项目强烈推荐
3. **渐进式引入**：从新模块开始加注解，老模块逐步补全。pyright 对未注解代码也能做部分推断
4. **避免运行时类型检查**：除非用 Pydantic 等框架，不要在运行时手动检查类型——这是 Python 的反模式

> 💡 性能口诀：注解零开销，检查离线做，团队用 strict，脚本可跳过。

#### 踩坑日记：以为类型注解是运行时检查

> 📝 第一人称踩坑记录

"刚从 Java 转 Python 时，我给所有函数加了类型注解，以为像 Java 一样运行时会检查类型。直到有一天，QA 报了一个 bug：某个函数接收了字符串但注解写的是 int，程序没报错，只是产生了奇怪的结果。

我花了两个小时排查——以为是缓存问题、以为是序列化问题——最后才发现：**Python 的类型注解运行时不检查！** `def f(x: int)` 传入字符串照样运行，只是 mypy 会报错。但我从来没跑过 mypy。

从那以后，我在 `pre-commit` 钩子里加了 `mypy --strict`，CI 里也加了类型检查门禁。Python 的类型安全是'自愿'的——但自愿不等于不做。"

#### 本章小结

1. **自愿安检哲学**：Python 类型注解是"自愿"的——运行时零检查零开销，类型安全由 mypy/pyright 离线提供 —— 像地铁自愿安检，走不走由你
2. **渐进式类型系统**：从 PEP 484（3.5）到 PEP 695（3.12），Python 用 8 年建立了完整的类型系统 —— 每个版本都向后兼容，可以渐进引入
3. **Protocol > Interface**：Protocol 的结构化子类型让第三方类无需修改即可适配，比 Java Interface 灵活得多 —— 像默契约定 vs 正式合同
4. **工具双雄**：mypy 是 PEP 484 的灵感来源，pyright 是微软的高性能替代 —— 个人用 pyright，CI 两者都用
5. **PEP 695 是分水岭**：Python 3.12 的泛型新语法让 Python 的类型表达力追上了 Java，`class C[T]:` 比 `class C<T>` 更简洁 —— 从冗长到优雅
