### 第17章 测试：从JUnit到pytest的降维打击

> 📖 本章你将学会：
> - 理解pytest"测试就是函数"的哲学，对比JUnit注解驱动的差异
> - 用fixture替代`@BeforeEach`/`@AfterEach`，掌握scope作用域与依赖注入
> - 用`@pytest.mark.parametrize`实现数据驱动测试
> - 用`conftest.py`实现跨文件fixture共享
- 掌握pytest-xdist并行测试与pytest-cov覆盖率分析

#### 第1节 JUnit vs pytest：两种测试哲学

Java老兵写测试，肌肉记忆是这样的：

```java
// JUnit 5: 注解驱动，必须放在类里
@ExtendWith(MockitoExtension.class)
class UserServiceTest {

    @Mock
    UserRepository repo;

    @InjectMocks
    UserService service;

    @BeforeEach
    void setup() {
        MockitoAnnotations.openMocks(this);
    }

    @Test
    @DisplayName("should find user by id")
    void shouldFindUser() {
        when(repo.findById(1L)).thenReturn(Optional.of(new User("Alice")));
        User user = service.findById(1L);
        assertEquals("Alice", user.getName());
        verify(repo, times(1)).findById(1L);
    }

    @Test
    @DisplayName("should throw when user not found")
    void shouldThrowWhenNotFound() {
        when(repo.findById(99L)).thenReturn(Optional.empty());
        assertThrows(UserNotFoundException.class, () -> service.findById(99L));
    }
}
```

同样的逻辑，pytest写法：

```python
# pytest: 函数驱动，不需要类
def test_find_user(mock_repo):
    mock_repo.find_by_id.return_value = User(name="Alice")
    user = UserService(mock_repo).find_by_id(1)
    assert user.name == "Alice"
    mock_repo.find_by_id.assert_called_once_with(1)

def test_throws_when_not_found(mock_repo):
    mock_repo.find_by_id.return_value = None
    import pytest
    with pytest.raises(UserNotFoundError):
        UserService(mock_repo).find_by_id(99)
```

pytest的核心哲学：**测试就是函数**。不需要`@Test`注解，不需要类，以`test_`开头的函数就是测试用例。`assert`语句替代`assertEquals`/`assertThrows`等断言方法——如果assert失败，pytest通过断言重写（assertion rewriting）技术自动显示丰富的失败信息。

> 💡 比喻：JUnit像写公文——`@Test`盖章、`@BeforeEach`流程、`assertEquals`固定格式，每个环节有模板。pytest像写便签——函数写好、assert一行、完事了。JUnit的注解是"格式约束"，pytest的约定是"命名即识别"。

##### 1.1 assert重写：pytest的黑科技

pytest最令人惊艳的特性之一是**断言重写**——它在运行时动态改写你写的普通`assert`语句，当断言失败时，自动展示变量的实际值与期望值之间的差异。

```python
def test_dict_equality():
    actual = {"name": "Alice", "age": 30, "role": "user"}
    expected = {"name": "Alice", "age": 25, "role": "admin", "active": True}
    assert actual == expected
```

运行后pytest输出：

```
E       AssertionError: assert {'name': 'Alice', 'age': 30, 'role': 'user'} == {'name': 'Alice', 'age': 25, 'role': 'admin', 'active': True}
E         Common items:
E         {'name': 'Alice'}
E         Differing items:
E         {'age': 30} != {'age': 25}
E         {'role': 'user'} != {'role': 'admin'}
E         Left contains 1 more item:
E         {'active': True} ← expected中有但actual中缺失
```

对比JUnit，你需要手写`assertEquals`、`assertThat`、Hamcrest matcher来获得类似的可读性。pytest用一行`assert`就做到了，而且是Python原生语法。

##### 1.2 异常测试

```python
import pytest

# pytest: 用上下文管理器
def test_divide_by_zero():
    with pytest.raises(ZeroDivisionError, match="division by zero"):
        result = 1 / 0

# JUnit: assertThrows
// assertThrows(ZeroDivisionError.class, () -> calculator.divide(1, 0));
```

`pytest.raises`还支持`match`参数做正则匹配异常消息，以及通过`excinfo`对象检查异常详情：

```python
def test_custom_exception():
    with pytest.raises(ValueError) as excinfo:
        raise ValueError("user not found: id=999")
    assert "id=999" in str(excinfo.value)
    assert excinfo.type is ValueError
```

#### 第2节 fixture：`@BeforeEach`的进化版

fixture是pytest区别于其他测试框架的标志性设计。它不是简单的setup/teardown函数，而是一套**声明式、作用域可控、自动依赖注入**的资源管理模型。[^pytest-fixture]

##### 2.1 基础fixture

```python
import pytest
from myapp.database import create_session, User

@pytest.fixture
def db_session():
    """每个测试函数前后自动执行setup和teardown"""
    # --- setup ---
    session = create_session("sqlite:///:memory:")
    session.execute("CREATE TABLE users (id INT, name TEXT)")
    yield session  # ← yield之前是setup，yield的值注入给测试，yield之后是teardown
    # --- teardown ---
    session.close()

def test_user_count(db_session):  # ← 参数名"db_session"匹配fixture名，自动注入
    db_session.add(User(id=1, name="Alice"))
    assert db_session.query(User).count() == 1

def test_user_name(db_session):  # ← 同一个fixture，但每个测试拿到全新session
    db_session.add(User(id=2, name="Bob"))
    user = db_session.query(User).first()
    assert user.name == "Bob"
```

对比JUnit：

```java
// JUnit 5
class UserServiceTest {
    private Session session;

    @BeforeEach
    void setup() {
        session = createSession("sqlite:///:memory:");
        session.execute("CREATE TABLE users (id INT, name TEXT)");
    }

    @AfterEach
    void teardown() {
        session.close();
    }

    @Test
    void testUserCount() {
        session.add(new User(1, "Alice"));
        assertEquals(1, session.query(User.class).count());
    }
}
```

| 特性 | JUnit `@BeforeEach` | pytest fixture |
|------|--------------------|-----------------|
| 声明方式 | 方法注解 | `@pytest.fixture`装饰器 |
| 注入方式 | 手动赋值给字段 | 参数名自动匹配，依赖注入 |
| 作用域 | 仅方法级 | function/class/module/package/session五级 |
| 跨测试共享 | 需要静态字段 | fixture本身即可共享 |
| 依赖链 | 手动管理 | 自动解析依赖图 |
| 复用性 | 每个测试类重新写 | `conftest.py`全局共享 |

##### 2.2 fixture的五种作用域

```python
import pytest

@pytest.fixture(scope="function")  # 默认：每个测试函数创建一次
def fresh_db():
    db = Database()
    yield db
    db.close()

@pytest.fixture(scope="class")  # 每个测试类创建一次
def class_db():
    db = Database()
    yield db
    db.close()

@pytest.fixture(scope="module")  # 每个测试文件创建一次
def module_config():
    return load_config("test_config.yml")

@pytest.fixture(scope="package")  # 每个测试包创建一次
def package_cache():
    return Cache()

@pytest.fixture(scope="session")  # 整个测试会话创建一次（最昂贵资源）
def test_server():
    server = start_test_server()
    yield server  # 所有测试共用一个服务器实例
    server.stop()
```

> ⚡ 作用域选择原则：**越昂贵的资源用越大的作用域**。数据库连接用session级（启动一次，所有测试共用），临时文件用function级（每个测试独立），配置文件用module级。JUnit只有方法级（`@BeforeEach`）和类级（`@BeforeAll`），缺少中间粒度。

##### 2.3 fixture依赖链

fixture可以依赖其他fixture，pytest自动解析依赖图并按需执行：

```python
@pytest.fixture(scope="session")
def test_server():
    server = start_test_server()
    yield server
    server.stop()

@pytest.fixture(scope="session")
def db_connection(test_server):  # ← 依赖test_server，pytest保证先执行test_server
    conn = test_server.get_db_connection()
    yield conn
    conn.close()

@pytest.fixture
def clean_db(db_connection):  # ← 依赖db_connection（session级），自身function级
    db_connection.execute("DELETE FROM users")
    yield db_connection
    db_connection.rollback()

def test_create_user(clean_db):  # ← 依赖链：test_server → db_connection → clean_db
    clean_db.execute("INSERT INTO users VALUES (1, 'Alice')")
    assert clean_db.query("SELECT count(*) FROM users") == 1
```

pytest会自动：
1. 启动test_server（session级，只启动一次）
2. 获取db_connection（session级，依赖test_server）
3. 每个测试前清理clean_db（function级，依赖db_connection）
4. 测试后回滚clean_db
5. 全部测试完成后关闭db_connection和test_server

##### 2.4 autouse：自动执行的fixture

```python
@pytest.fixture(autouse=True)
def reset_environment(monkeypatch):
    """每个测试自动执行，无需在测试函数参数中声明"""
    monkeypatch.setenv("APP_ENV", "test")
    monkeypatch.setattr("time.time", lambda: 1700000000.0)
    yield
    # 每个测试后自动恢复所有patch
```

`autouse=True`的fixture不需要在测试函数参数中声明，会自动应用到作用域内的所有测试。适合做全局环境重置。

#### 第3节 参数化测试：一个函数覆盖N个场景

##### 3.1 基础参数化

```python
@pytest.mark.parametrize("input,expected", [
    ("hello", 5),
    ("world", 5),
    ("", 0),
    ("Python", 6),
    ("你好", 2),       # 中文字符也算一个字符
    ("a b c", 5),     # 包含空格
])
def test_string_length(input, expected):
    assert len(input) == expected
```

一个装饰器生成6个测试用例。对比JUnit，需要6个`@Test`方法，或用`@ParameterizedTest`+`@CsvSource`：

```java
// JUnit 5
@ParameterizedTest
@CsvSource({
    "hello, 5",
    "world, 5",
    "'', 0",
    "Python, 6"
})
void testStringLength(String input, int expected) {
    assertEquals(expected, input.length());
}
```

##### 3.2 带ID的参数化

```python
@pytest.mark.parametrize(
    "user_input,expected",
    [
        ("admin@example.com", True),
        ("invalid-email", False),
        ("", False),
        ("user@.com", False),
    ],
    ids=["valid email", "no @ symbol", "empty string", "missing domain"]
)
def test_email_validation(user_input, expected):
    assert validate_email(user_input) == expected
```

`ids`参数给每个用例起名字，失败时输出更易读：

```
test_email_validation[valid email] PASSED
test_email_validation[no @ symbol] PASSED
test_email_validation[empty string] PASSED
test_email_validation[missing domain] PASSED
```

##### 3.3 多参数组合

```python
@pytest.mark.parametrize("username", ["alice", "bob", "admin"])
@pytest.mark.parametrize("role", ["user", "editor", "admin"])
def test_permission_matrix(username, role):
    """3×3=9个测试用例，覆盖用户名×角色组合"""
    permissions = get_permissions(username, role)
    if role == "admin":
        assert "delete" in permissions
    else:
        assert "delete" not in permissions
```

多个`parametrize`叠加会做笛卡尔积——3个用户名 × 3个角色 = 9个测试用例。

##### 3.4 fixture参数化

fixture本身也可以参数化，让依赖它的所有测试自动跑多轮：

```python
@pytest.fixture(params=["sqlite", "postgresql", "mysql"])
def db_engine(request):
    """每个依赖此fixture的测试都会跑3次——每个数据库一次"""
    engine = create_engine(request.param)
    yield engine
    engine.dispose()

def test_create_table(db_engine):  # ← 自动跑3次
    db_engine.execute("CREATE TABLE test (id INT)")
    assert db_engine.has_table("test")

def test_insert(db_engine):  # ← 也自动跑3次
    db_engine.execute("INSERT INTO test VALUES (1)")
    assert db_engine.query("SELECT count(*) FROM test") == 1
```

#### 第4节 `conftest.py`：跨文件fixture共享

`conftest.py`是pytest的特殊文件——放在其中的fixture**自动可用**于同目录及子目录下的所有测试文件，无需import。

```
myproject/
├── src/
│   └── myapp/
├── tests/
│   ├── conftest.py          # ← 全局fixture，所有测试可用
│   ├── unit/
│   │   ├── conftest.py      # ← unit测试专用fixture
│   │   └── test_service.py
│   └── integration/
│       ├── conftest.py      # ← integration测试专用fixture
│       └── test_api.py
```

```python
# tests/conftest.py —— 全局fixture
import pytest
from myapp.app import create_app
from myapp.database import create_engine

@pytest.fixture(scope="session")
def app():
    """整个测试会话共用一个app实例"""
    app = create_app(testing=True)
    with app.app_context():
        yield app

@pytest.fixture(scope="session")
def test_client(app):
    """Flask测试客户端"""
    return app.test_client()

@pytest.fixture
def db_session(app):
    """每个测试函数独立的数据库会话"""
    engine = create_engine(app.config["TEST_DATABASE_URL"])
    session = Session(engine)
    yield session
    session.rollback()
    session.close()

@pytest.fixture
def mock_external_api(monkeypatch):
    """Mock外部API调用"""
    def mock_response(url, **kwargs):
        return {"status": "ok", "data": {"users": []}}
    monkeypatch.setattr("requests.get", mock_response)
```

```python
# tests/unit/test_service.py —— 无需import conftest
def test_create_user(db_session, mock_external_api):
    """db_session和mock_external_api自动从conftest注入"""
    service = UserService(db_session)
    user = service.create("alice@example.com")
    assert user.id is not None
    assert user.email == "alice@example.com"
```

> 💡 比喻：JUnit的`@BeforeEach`像每份文件都要手写"以下为附件清单"——每个测试类重复声明setup。pytest的`conftest.py`像办公室的公用打印机——放在那里，所有人自动可用，不用搬来搬去。

#### 第5节 pytest插件生态：扩展测试能力

##### 5.1 pytest-xdist：并行测试

```bash
# 安装
pip install pytest-xdist

# 按CPU核心数自动并行
pytest -n auto

# 指定4个进程并行
pytest -n 4

# 按文件分配负载（I/O密集型测试更稳定）
pytest -n 4 --dist=loadfile
```

pytest-xdist将测试分发到多个CPU核心并行执行。8000个测试从45分钟降到12分钟。[^pytest-xdist]

> ⚠ 并行测试注意事项：共享状态（数据库、文件）的测试需要隔离。可用`os.environ.get("PYTEST_XDIST_WORKER", "0")`获取worker ID，每个worker使用独立的数据库schema。

##### 5.2 pytest-cov：覆盖率分析

```bash
# 安装
pip install pytest-cov

# 统计src/目录覆盖率
pytest --cov=src/

# 生成HTML报告
pytest --cov=src/ --cov-report=html

# 终端报告 + 显示未覆盖行
pytest --cov=src/ --cov-report=term-missing

# 设置覆盖率阈值（CI/CD质量门禁）
pytest --cov=src/ --cov-fail-under=90
```

pytest-cov 5.0.0（2024年3月发布）基于coverage.py，支持子进程覆盖率和xdist并行覆盖率合并。[^pytest-cov]

##### 5.3 pytest-asyncio：异步测试

```python
import pytest
import asyncio

@pytest.mark.asyncio
async def test_async_api():
    """直接写async测试函数，pytest自动管理事件循环"""
    result = await async_fetch_user(1)
    assert result.name == "Alice"

@pytest.fixture
async def async_db_session():
    """异步fixture"""
    session = await create_async_session()
    yield session
    await session.close()
```

pytest 8.0原生兼容async/await语法，配合pytest-asyncio插件可以精细控制事件循环策略。[^pytest-8-async]

##### 5.4 pytest-mock：便捷Mock

```python
def test_with_mock(mocker):
    """mocker fixture自动从pytest-mock注入"""
    mock = mocker.patch("myapp.service.external_api_call")
    mock.return_value = {"status": "ok"}

    result = my_function()
    assert result["success"] is True
    mock.assert_called_once()
```

| 插件 | 功能 | 用法 |
|------|------|------|
| `pytest-xdist` | 并行测试 | `pytest -n auto` |

#### 第6节 pytest配置

现代项目推荐在`pyproject.toml`中配置pytest：

```toml
# pyproject.toml
[tool.pytest.ini_options]
testpaths = ["tests"]              # 测试目录
python_files = ["test_*.py"]       # 测试文件命名规则
python_functions = ["test_*"]      # 测试函数命名规则
addopts = [
    "-v",                          # 详细输出
    "--tb=short",                  # 简洁traceback
    "--strict-markers",            # 未注册marker报错
    "--strict-config",             # 配置错误报错
    "--cov=src",                   # 覆盖率统计
    "--cov-report=term-missing",   # 显示未覆盖行
    "--cov-fail-under=80",         # 覆盖率阈值
]
markers = [
    "slow: marks tests as slow (deselect with '-m \"not slow\"')",
    "integration: marks tests as integration tests",
    "smoke: critical path tests",
    "flaky: known flaky tests",
]
filterwarnings = [
    "error",                       # warning当作error
    "ignore::DeprecationWarning",  # 忽略特定warning
]
```

常用运行命令：

```bash
pytest                           # 运行所有测试
pytest tests/test_api.py         # 运行指定文件
pytest -k "login"                # 运行名字含"login"的测试
pytest -m "not slow"             # 排除slow标记的测试
pytest -m "smoke"                # 只跑smoke测试
pytest --lf                      # 只跑上次失败的测试
pytest -x                        # 遇到第一个失败就停止
pytest -n auto                   # 并行执行
pytest --durations=10            # 显示最慢的10个测试
```

#### 本章小结

pytest用**函数式测试 + fixture依赖注入 + 参数化**三板斧，把JUnit的注解样板代码砍掉了70%。`assert`语句配合断言重写，自动生成比JUnit更丰富的失败诊断信息。fixture的五级作用域和自动依赖链，让资源管理比JUnit的`@BeforeEach`/`@AfterEach`灵活得多。`conftest.py`实现跨文件fixture共享，无需import。插件生态覆盖并行测试、覆盖率、异步测试、Mock等全场景。

Java的测试是"注解驱动的模板填写"，pytest的测试是"函数驱动的自由表达"——但自由不意味着随意，约定（`test_`前缀、fixture参数注入）替代了约束（`@Test`注解），反而更简洁。
