### 第24章 性能优化实战案例：三个真实场景

> 📖 本章你将学会：
> - 在数据处理管道中应用Pandas+NumPy向量化
> - 在Web API中应用asyncio+连接池
> - 在CPU密集型计算中应用numba+multiprocessing
> - 掌握"定位→分析→优化→验证"的完整工作流

#### 第1节 案例一：数据处理管道优化

**场景**：清洗1000万行CSV数据，按城市分组统计平均薪资，取Top 10。

**Java老兵的第一反应**——用Stream API：

```java
// Java Stream方案——约8秒
Map<String, Double> result = Files.lines(Path.of("salaries.csv"))
    .skip(1) // 跳过表头
    .map(line -> line.split(","))
    .collect(Collectors.groupingBy(
        fields -> fields[2], // city
        Collectors.averagingDouble(fields -> Double.parseDouble(fields[3])) // salary
    ))
    .entrySet().stream()
    .sorted(Map.Entry.<String, Double>comparingByValue().reversed())
    .limit(10)
    .collect(Collectors.toMap(...));
```

**纯Python循环方案**——最直觉但最慢：

```python
from collections import defaultdict

salaries_by_city = defaultdict(list)
with open("salaries.csv") as f:
    next(f)  # 跳过表头
    for line in f:
        fields = line.strip().split(",")
        city = fields[2]
        salary = float(fields[3])
        salaries_by_city[city].append(salary)

avg_by_city = {city: sum(s) / len(s) for city, s in salaries_by_city.items()}
top10 = sorted(avg_by_city.items(), key=lambda x: x[1], reverse=True)[:10]
```

**Pandas向量化方案**——4行代码，最快：

```python
import pandas as pd

df = pd.read_csv("salaries.csv")
result = df.groupby("city")["salary"].mean().nlargest(10)
```

**性能对比**：

| 方案 | 代码量 | 执行时间 | 内存峰值 |
|------|--------|---------|---------|
| Java Stream | ~30行 | ~8s | ~2GB |
| 纯Python循环 | ~15行 | ~45s | ~3GB |
| Pandas向量化 | 4行 | ~1.2s | ~800MB |

Pandas为什么快：`read_csv` 用C解析器逐块读取；`groupby` 在NumPy数组上做向量化聚合；`nlargest` 用堆排序而非全排序。整个管道几乎不经过Python解释器。

**Java老兵的反思**：在Java中，数据处理通常用Stream API——它优雅但不是最快的（装箱开销、函数式接口调用）。如果Java用原始数组+手写循环，可以更快但代码冗长。Python+Pandas的优势是"既快又简洁"——向量化让代码简洁，C底层让速度飞快。

#### 第2节 案例二：Web API响应优化

**场景**：一个API需要聚合10个微服务的响应，每个微服务平均响应100ms。

**Java方案**——CompletableFuture并发：

```java
// Java CompletableFuture——10线程并发
List<CompletableFuture<String>> futures = urls.stream()
    .map(url -> CompletableFuture.supplyAsync(() -> callApi(url), executor))
    .collect(Collectors.toList());

CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).join();
List<String> results = futures.stream()
    .map(CompletableFuture::join)
    .collect(Collectors.toList());
// 总耗时：~150ms（10个请求并发，取最慢的+线程调度开销）
```

**Python threading方案**——受GIL限制：

```python
from concurrent.futures import ThreadPoolExecutor
import requests

def fetch(url):
    return requests.get(url).json()

with ThreadPoolExecutor(max_workers=10) as executor:
    results = list(executor.map(fetch, urls))
# 总耗时：~800ms（GIL在JSON解析时争抢，实际并发度低）
```

**Python asyncio方案**——单线程协程：

```python
import asyncio
import aiohttp

async def fetch(session, url):
    async with session.get(url) as resp:
        return await resp.json()

async def main():
    async with aiohttp.ClientSession() as session:
        results = await asyncio.gather(*[fetch(session, url) for url in urls])

asyncio.run(main())
# 总耗时：~120ms（单线程协程并发，无GIL争抢，无线程切换开销）
```

**性能对比**：

| 方案 | 10个API各100ms | 总耗时 | 原因 |
|------|---------------|--------|------|
| Java CompletableFuture | 10线程并发 | ~150ms | 线程调度+装箱开销 |
| Python threading | 10线程+GIL | ~800ms | GIL在JSON解析时争抢 |
| Python asyncio | 10协程并发 | ~120ms | 单线程，无切换开销 |

asyncio最快——IO等待期间协程挂起不占资源，无GIL争抢（IO操作释放GIL），无线程切换开销。

> ⚡ **关键认知**：IO密集型任务，asyncio是Python的最佳选择。它比threading快（无GIL争抢），比Java的线程方案更轻量（协程切换~100ns vs 线程切换~1μs）。详见第三篇第15章。

#### 第3节 案例三：CPU密集型计算

**场景**：蒙特卡洛模拟——计算π的近似值，模拟1000万次随机点投掷。

```python
import random
import math

# 基础版本——纯Python
def monte_carlo_pi_pure(n):
    inside = 0
    for _ in range(n):
        x = random.random()
        y = random.random()
        if x * x + y * y <= 1.0:
            inside += 1
    return 4.0 * inside / n
```

**优化1：numba @njit**

```python
from numba import njit
import numpy as np

@njit
def monte_carlo_pi_numba(n):
    inside = 0
    for _ in range(n):
        x = np.random.random()
        y = np.random.random()
        if x * x + y * y <= 1.0:
            inside += 1
    return 4.0 * inside / n
```

一行 `@njit` 装饰器，循环编译为机器码。

**优化2：numba + multiprocessing**

```python
from multiprocessing import Pool
import numpy as np
from numba import njit

@njit
def _mc_chunk(n):
    inside = 0
    for _ in range(n):
        x = np.random.random()
        y = np.random.random()
        if x * x + y * y <= 1.0:
            inside += 1
    return inside

def monte_carlo_pi_parallel(n, processes=4):
    chunk = n // processes
    with Pool(processes) as pool:
        results = pool.map(_mc_chunk, [chunk] * processes)
    return 4.0 * sum(results) / n
```

**优化3：NumPy向量化**

```python
import numpy as np

def monte_carlo_pi_numpy(n):
    x = np.random.random(n)
    y = np.random.random(n)
    inside = np.sum(x * x + y * y <= 1.0)
    return 4.0 * inside / n
```

**性能对比**：

| 方案 | 1000万次耗时 | 加速倍数 |
|------|-------------|---------|
| 纯Python单进程 | ~30s | 1x (基准) |
| numba @njit 单进程 | ~0.8s | ~37x |
| numba + 4进程并行 | ~0.3s | ~100x |
| NumPy向量化 | ~0.15s | ~200x |
| Java (同等循环) | ~2s | ~15x |

> ⚠️ 以上数据为典型场景示意值，实际效果取决于CPU核心数和频率。

**方案选择分析**：

- **NumPy向量化最快**（~200x）——因为 `np.random.random(n)` 一次生成1000万个随机数（C层面批量），`x*x + y*y <= 1.0` 是向量化比较，`np.sum` 是向量化归约。全程无Python循环。
- **numba + 并行次快**（~100x）——JIT编译消除了循环开销，4进程利用了多核。但进程间通信和启动有额外成本。
- **纯numba单进程**（~37x）——JIT编译有效但单核限制。

**最佳实践**：如果逻辑可以向量化（如本例），优先用NumPy。如果逻辑太复杂无法向量化（如带状态分支的模拟），用numba+multiprocessing。

#### 第4节 优化工作流：定位→分析→优化→验证

三个案例体现了统一的性能优化工作流：

```
定位 → 分析 → 优化 → 验证
  │       │       │       │
  │       │       │       └─ 用timeit/benchmark确认收益
  │       │       └─ 选择工具：NumPy/asyncio/numba/...
  │       └─ cProfile/line_profiler找到瓶颈
  └─ py-spy/cProfile找到热点
```

**步骤1：定位热点**

```bash
# py-spy采样——生产环境友好
py-spy record -o profile.svg -- python my_app.py
# 或cProfile——开发环境精确
python -m cProfile -s cumulative my_app.py | head -20
```

**步骤2：分析根因**

根据热点类型判断优化方向：

| 热点类型 | 优化工具 | 案例 |
|---------|---------|------|
| 数值循环 | NumPy向量化 / numba | 案例三蒙特卡洛 |
| IO等待 | asyncio / 连接池 | 案例二Web API |
| 数据处理 | Pandas向量化 | 案例一CSV清洗 |
| 对象创建过多 | __slots__ / 生成器 | 第22章内存优化 |
| C扩展内部 | py-spy --native / perf | 深度分析 |

**步骤3：实施优化**

一次只改一个变量——不要同时换两个工具，否则无法判断哪个起了作用。

**步骤4：验证收益**

```python
import timeit

# 优化前后对比
time_before = timeit.timeit('monte_carlo_pi_pure(100000)', globals=globals(), number=10)
time_after = timeit.timeit('monte_carlo_pi_numpy(100000)', globals=globals(), number=10)
print(f"加速: {time_before / time_after:.1f}x")
```

#### 本章小结

三个案例展示了Python性能优化的核心策略：

数据处理用Pandas向量化——C解析器+C层面聚合，代码简洁且速度飞快。案例一中4行Pandas代码替代30行Java Stream，速度快6倍。

IO密集型用asyncio——单线程协程并发，无GIL争抢，无线程切换开销。案例二中asyncio比threading快6倍，比Java线程方案快20%。

CPU密集型用numba+multiprocessing——JIT编译消除循环开销，多进程利用多核。案例三中200倍加速（NumPy向量化）或100倍加速（numba并行）。

统一工作流：py-spy/cProfile定位热点 → 判断瓶颈类型 → 选择对应工具 → timeit验证收益。

> 💡 **Java老兵总结**：Python性能优化的思路和Java完全不同。Java优化JVM参数（堆大小、GC策略、JIT预热）；Python优化执行方式（向量化、JIT编译、异步IO）。Python的优化更直接——用对的工具解决对的问题，不需要理解复杂的JVM内部机制。这就是Python的哲学：简单直接，但需要你知道什么时候用什么工具。

#### 📝 Java老兵踩坑日记：在Python里做对象池的那次

Java的性能优化思维里，"对象池"是标配——减少GC压力，复用对象。所以我看到Python代码里 `User()` 创建了一百万个对象，第一反应是："这GC不得疯了？得用对象池！"

我花了半天写了个 `UserPool`，预分配100万个User对象循环复用。跑完benchmark，性能**反而下降了15%**。

为什么？因为Python的内存管理和Java完全不同：

Java的对象池减少的是**GC停顿**（Young GC频繁触发的问题）。Python用的是**引用计数**——对象引用计数归零立即释放，没有"GC停顿"问题。Python对象池反而增加了引用计数管理的开销（对象被反复引用/解引用）。

更关键的是，Python对象的 `__dict__` 哈希表比Java对象头大得多，对象池复用反而让 `__dict__` 的旧数据残留，需要额外清理。

从那天起，我学到了：**不要把Java的性能优化套路搬到Python。** Python的性能瓶颈不在对象创建（引用计数很快），而在**循环执行**（动态类型开销）——优化方向是用NumPy向量化替代for循环，而不是做对象池。
